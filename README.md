# Megavibe

**Give Claude Code a memory that survives compaction, crashes and new sessions.**

Megavibe keeps decisions, mistakes, progress and context in files on disk, so a
fresh session can pick up where the last one stopped instead of re-deriving
everything from a lossy summary.

**Before you paste the install command**, know what it does to your machine — it
installs CLIs and MCP servers, and it launches Claude with permission prompts
disabled by default. See [Security and what gets installed](#security-and-what-gets-installed).

Requires a [Claude Code](https://docs.anthropic.com/en/docs/claude-code)
subscription. macOS and Linux (Windows via Git Bash/WSL, less tested); the
context watcher needs `tmux`.

## Security and what gets installed

Megavibe is installed with `curl | bash` and then changes how Claude Code runs.
Stated plainly, because you should decide before pasting:

- **Permission prompts are disabled by default.** The `megavibe` wrapper launches
  Claude with `--dangerously-skip-permissions`, so the agent acts without asking.
  That is the point (unattended runs), and it is a real trade — run plain `claude`
  in a project if you want prompts back.
- **Commits get a co-author trailer** (`megavibe <megavibe@poma-ai.com>`) so
  agent-assisted commits are identifiable. Change it in
  `~/.claude/settings.json` under `attribution`, or clear it.
- **MCP servers are registered** user-wide: Gemini and Playwright if their CLIs
  are present, plus the bundled poma-memory semantic search. Codex is NOT an MCP
  server — codex-cli 0.154.0 removed its `mcp-server` subcommand, so megavibe
  calls it through `~/.megavibe/scripts/codex-review.sh` over `codex exec` and
  removes any dead registration left by an earlier setup.
  A Codex review runs with the project read-only and a throwaway scratch directory
  writable (no network), so it can run the harnesses a review needs; `--strict` or
  `MEGAVIBE_CODEX_SCRATCH=0` makes it fully read-only. It refuses to run while
  `~/.codex/config.toml` (or `$CODEX_HOME/config.toml`) sets `openai_base_url` or
  `chatgpt_base_url` at the top level or in the active profile
  (`MEGAVIBE_CODEX_ALLOW_ENDPOINT=1` allows it). That check reads the file line by
  line: quoted keys, dotted keys, inline tables and multi-line strings are not parsed.
- **Hooks run on every tool call** in projects you initialise — they write context
  files under `.agent/` and never send anything off your machine on their own.
- **Backends see your content.** Delegating to Gemini or Codex sends the material
  to those providers. Whether they train on it depends on your account with
  them — for the Gemini API, only a key from a project **with billing attached**
  is a "Paid Service" (prompts not used for training); a Workspace login does
  not change that for the API, and the free tier trains on your prompts.

## Get Started

### 1. Open a terminal

- **macOS**: Press **Cmd + Space**, type **Terminal**, press **Enter**
- **Linux**: Open your terminal emulator
- **Windows**: Open **Git Bash** (from [git-scm.com](https://git-scm.com)) or **WSL**

### 2. Install Megavibe

Copy-paste this into Terminal and press Enter:

```bash
curl -fsSL https://raw.githubusercontent.com/poma-ai/megavibe/main/install.sh | bash
```

The installer detects your OS and package manager (Homebrew, apt, dnf, pacman, winget, choco) and installs everything needed — Node.js, Python, jq, AI tools — then walks you through each step. Takes about 5 minutes.

Run unattended (stdin not a terminal, as in an agent's shell or a script), `install.sh` and `setup.sh` never wait for an answer: setup takes the automatic install and skips the Gemini key prompt, and both run `sudo` with `-n`, so a package install that would need a password fails at once with a hint instead of hanging (re-run from a terminal, or install that package yourself). The `curl | bash` installer sets `MEGAVIBE_TTY_PROMPT=1`, which lets setup's key and `sudo` prompts reach your terminal when its output is visible there.

### 3. Use it

Navigate to any project and run:

```bash
cd ~/my-project
megavibe
```

That's it. Claude now remembers everything you work on together. Run `megavibe` every time you start working — it's always safe to re-run.

Every session automatically has **Remote Control** enabled — you can connect from your phone via the Claude app at any time (see [Remote Control](#remote-control) below).

Launcher commands:

```bash
megavibe --help       # launcher commands and options (also -h or help)
megavibe --version    # installed commit, or unknown (also -V or version)
megavibe restart-all [--dry-run] [--others]  # report sessions needing manual restart
```

Help and version work only as the first argument and exit without setup, updates,
project changes or starting Claude. The version comes from `$MEGAVIBE_HOME/version`
(default `~/.megavibe/version`), shortened to eight characters, with a date if the
record includes one. Other arguments pass through to Claude Code, except for the
launcher's own commands/options and a lone unknown subcommand; see `claude --help`
for Claude's options. For example, `megavibe --model sonnet --help` forwards
`--help` to Claude after the launcher's normal project setup.

The launcher refuses to bootstrap the install directory itself (`$MEGAVIBE_HOME`,
default `~/.megavibe`). Commands that do not bootstrap, including help, version,
update and node, still work there.

## What Does It Actually Do?

### The problem

Claude Code forgets things. Every time it "compacts" (runs out of memory), it loses detail. After a few compactions, it forgets constraints, repeats mistakes, and loses track of decisions.

### The solution

Megavibe creates a **durable memory layer** that Claude writes to continuously and recovers from automatically:

```
your-project/
├── .agent/                          <- Claude's memory (survives everything)
│   ├── FULL_CONTEXT.md              <- everything that happened (append-only)
│   ├── DECISIONS.md                 <- why things were done a certain way
│   ├── TASKS.md                     <- what's done, what's pending
│   ├── LESSONS.md                   <- patterns from your corrections
│   └── sessions/{id}/
│       └── WORKING_CONTEXT.md       <- focused summary (~400 lines)
│
├── .claude/                         <- automation (hooks, rules, skills)
│   ├── hooks/                       <- auto-logging, safety, search
│   ├── rules/                       <- extended protocols
│   ├── skills/                      <- slash commands (/catchup, /rehydrate)
│   └── settings.json                <- hook configuration
│
└── CLAUDE.local.md                  <- your personal overrides (gitignored)
```

**How recovery works:**

1. An **out-of-band watcher daemon** reads the live transcript and writes summaries to `.agent/` files between turns — no in-session token tax, on by default. (Hook-based nudges are still there as a safety net when the watcher is off.)
2. When Claude's context gets compacted, a hook fires automatically
3. Claude calls Codex (or a built-in subagent, or Gemini) to read the full log and produce a focused summary
4. Claude reads the summary and continues — zero information loss, no human intervention

## Features

### Continuous out-of-band context flush (the watcher)

A background Python daemon (`~/.megavibe/scripts/context-watcher.py`) tails the live transcript JSONL and, on a 5-minute trickle, asks Codex (Gemini as fallback) to extract decisions, lessons, task changes, and a narrative recap — then writes them straight to `.agent/` files under `flock`. No in-session token cost, no prompts for Claude. Decisions are **staged** to a per-session queue for human review (low-stakes items auto-apply); review with `python3 ~/.megavibe/scripts/review-decisions.py`.

The watcher is on by default — set `MEGAVIBE_WATCHER=0` to opt out. When it's running, in-session tier nudges suppress automatically (no double-up). Full design and operations notes: **[README-watcher.md](README-watcher.md)**.

### Automatic context recovery

At high context, Claude saves decisions with reasons, tasks with owners and blockers, and a close-out summary event, then stamps `.agent/LOGS/.closeout-done.<sid12>` and continues working. It refreshes this state after each completed step, with or without the watcher. Claude Code compacts automatically; the session never asks you to compact, waits for compaction, or pauses, slows down or hands work back because of context level. It mentions compaction only if you ask, or once if auto-compaction is disabled in the session settings. Recovery below runs without prompting you.

Before the compaction, the pre-compact hook prints a short fixed list of what the summary must keep (open decisions, running background work with ids, the working-context and event-log paths, the next step); Claude Code passes a PreCompact hook's plain stdout to the compaction as instructions. The protocol's `Compact Instructions` section says the same. When Claude runs out of memory and compacts, megavibe detects it and triggers recovery. The hook writes the full orientation (git state, decisions, tasks, lessons, and the whole log when it is small) to `.agent/LOGS/rehydration-instructions.<session>.md` and gives Claude a short message pointing at it, because hook output over 10,000 characters reaches the model only as a 2,000-character preview. Then:

- **Normal case** (working context missing, or older than an event or register): Claude runs `/rehydrate`, which calls Codex (or the subagent) to produce a focused ~400-line `WORKING_CONTEXT.md`. With the context watcher on, events nearly always follow the last `/rehydrate`, so this is the usual case
- **Working context newer than every event and register** (`.agent/events/`, `snapshot.md`, `DECISIONS.md`, `TASKS.md`): Claude reads it and carries on; `/rehydrate` is optional and nothing reminds. The hook's message says which case applies and, when stale, how many events and registers were written after it
- **Empty context** (first compaction): instructs Claude to save the compaction summary before it's lost

**Ready to compact?** This check is advisory: run `.claude/hooks/compact-readiness.sh --session <session-id>` while refreshing the close-out; it does not require a manual compaction. Without `--session` it takes `$CLAUDE_CODE_SESSION_ID`, else the one tool-call counter touched in the last 24 hours (two is ambiguous and exits 2), so pass it whenever sessions share the project. Exit 0 means no findings in the observed state, 1 means `NOT READY` findings in the report, and 2 means unable to check (including missing `python3`). It never blocks a tool, Stop, or compaction. A body line starting with `DECISION:`, `D<number> `, `D<number>:` or `Decided:` asks for reconciliation of both `DECISIONS.md` and `TASKS.md`; backtick-fenced examples are ignored. Other decision-like prose is advisory. Three uncovered events also prompt task reconciliation (`MEGAVIBE_READY_TASKS_MIN_EVENTS`, default 3). Register mtimes and tool counters do not prove coverage.

After reviewing the events and reconciling both registers, run the same command with `--mark`. This records the observed event filenames in `.agent/.registers-checkpoint`: `covered-through <newest filename>` followed by covered filenames, one per line. Only membership establishes coverage; the header is descriptive. Same-second suffixes and late arrivals remain uncovered until marked. Marking records your assertion of review, then reports remaining findings: exit 1 can accompany a successful coverage write. It never certifies readiness or acknowledges pending rows. Legacy single-filename records are rejected, never migrated automatically. Reports create no files or locks; marking serializes coverage writes locally, while cloud replacement can still lose coverage. The existing coverage-aware `agent-log.sh fold` is retained: it refuses uncovered events, publishes the snapshot before removing events, and prunes identities at the snapshot's fold cutoff. Synchronize and review before folding; the report covers retained events, not history already in the snapshot.

Pending watcher rows are reported only as counts with their queue paths, regardless of timestamps or coverage records. No row IDs, receipts, handling markers, queue locks, or ownership migration are involved. Explicit full session IDs never select a sibling; exact short session directories remain exact. Unambiguous short aliases may resolve through session directories, background-state keys, or full queue/counter names. Ambiguous aliases or shared legacy queues report uncertainty (exit 2); the check never assigns their ownership or changes them.

Historical heartbeat nudges are advisory. Live running tasks without a heartbeat produce `NOT READY` findings only when supplied through `--hook-input <JSON_FILE>` (or `-` for stdin); otherwise coverage is unknown. The report uses the same task references and age interval as `watch-background.sh`. Working-context age and uncommitted work are informational. Finding and information previews are capped at 20 lines each; prose advisories default to 20 (`MEGAVIBE_READY_ADVISORY_LIMIT`, 0–1000), with 200 characters per detail line and omitted counts. Pre-compact alerts and tier 2/3 nudges carry advisory text (the alert capped at 6000 characters of text; a tier nudge at 2000 characters of its JSON-escaped form, so control characters count at their escaped length; each plus a truncation notice) and surface dependency failures.

**Register currency (optional).** If your `.agent/TASKS.md` opens with a "where we stand" section numbered 0, the pre-compact hook warns when that section's own date stamp is more than seven days old, and carries the warning into the message the session gets after the compaction. `MEGAVIBE_REGISTER_MAX_AGE_DAYS` changes the threshold.

It only reads a date the section *offers* as its stamp: bracketed in the heading — `## 0. Where we stand (2026-09-21)` — or a line beginning `As of 2026-09-21:`. Any other date is something the register talks about rather than when it was written, and reading "freeze was 2026-08-01" as a write time would report a register written today as fifty-one days old. A section with no stamp produces nothing; unknown is not the same as stale.

Everything else stays silent, including projects with no section 0. The staleness counter above tells you when a register was last *written*; this tells you how long ago it claims to have been *true*, which is the question that survives compaction badly.

Recovery allocates its first backend per [delegation.md](template/.claude/rules/delegation.md#universal-fallback-principle); `~/.megavibe/scripts/reviewers.sh digest-chain` supplies availability and failure fallbacks for this machine: ChatGPT/Codex → Claude subagent (always works, same subscription); on a machine without Codex, capped Gemini (API key) → Claude subagent. Measured on a 196 KB context log, Codex answers in 23 s on a small model at low effort, the subagent produces the richest summary but spends the session's own quota, and Gemini is the thinnest and the only one billed per token.

### Semantic search augmentation

Grep and Glob can recall historical `.agent/` notes alongside code search results. Bash content search is **off by default**; opt in with `MEGAVIBE_POMA_BASH=1`. Sessions that search through Bash rather than the Grep and Glob tools get little recall without it. Disabled Bash calls exit in the shell before Python starts and write no audit row. Recalled notes may be superseded: verify their claims against current code before stating them as fact.

Powered by [poma-memory](https://github.com/poma-ai/poma-memory) (pip-installed): hybrid BM25 + local vector search (model2vec), running locally. `reindex-agent.sh` refreshes the index after edits and Bash appends (debounced). The hook consumes structured `search --json` results and displays age from a leading filename date (`YYYY-MM-DD`, `YYYYMMDD`, or a compact timestamp), otherwise file mtime. Labels distinguish `dated YYYY-MM-DD (N days ago)`, `file modified N days ago (mtime; the text may be older)`, and `age unknown`. Exempt registers retain the same source-aware labels. Invalid calendar dates fall back to mtime with an explicit annotation; index timestamps never establish age. Notes older than `MEGAVIBE_POMA_MAX_AGE_DAYS` (default **45**) or with unknown age are withheld; `DECISIONS.md` and `LESSONS.md` are exempt from the age limit, but still need verification. File mtime is only a fallback, not proof that a claim was recently reviewed.

Recall excludes `FULL_CONTEXT.md`, `snapshot.md`, the project's own `.agent/TASKS.md` (the live task register, which `/catchup` and post-compact rehydration read directly; it was about half of the injected notes in one project's `injections.jsonl` audit; other projects' registers and nested files of that name are still recalled; it is matched by its resolved path, so a `.agent/TASKS.md` that is a symlink to a differently named file inside `.agent/` is still recalled; a target outside `.agent/` is not recalled at all), `WORKING_CONTEXT.md`, session and log files, self-written files and previously injected excerpts. Recognized searches inside `.agent/` skip recall. Bash parsing supports simple literal `grep`/`rg`/`ag`/`ack` and `git grep` commands, including `cd dir && ...` and `git -C dir grep ...`; parse ambiguity, pipelines and unknown options default to recall using the available query text, still subject to the age, lexical, path-exclusion and cap gates. Shell text is never executed. Explicit operational log/config targets skip recall; managed worktree ancestors do not. All three tools skip patterns with four or more regex alternatives or mostly ID-like tokens.

A cheap lexical gate requires two distinct query terms of at least four characters in the emitted excerpt, or the sole eligible term. It is case-insensitive and matches whole alphanumeric tokens, not synonyms or short symbols; it can miss useful notes and still accept irrelevant ones. `MEGAVIBE_POMA_MIN_SCORE` (default `0.028`) filters rank-fusion scores, **not absolute relevance**. `MEGAVIBE_POMA_TOPK` (default 8) controls candidates and `MEGAVIBE_POMA_MAX_RESULTS` (default 3; 0 disables injection) caps survivors. `MEGAVIBE_POMA_MAX_CHARS` (default 2400) caps each hit including its metadata, and `MEGAVIBE_POMA_MAX_TOTAL_CHARS` (default 6000) caps the full context including framing. Excerpts always start at the beginning of the context poma-memory returns (it may assemble several chunks, and its chunker keeps heading context) and are emitted whole when they fit. Longer contexts are cut at the last whitespace boundary within the budget (a Unicode-safe hard cut if none), with a visible ` [... truncated]` marker included in the cap. Text after the cut, such as a trailing status or rejection note, is lost: the marker means more exists. Oversized chunks with fewer than 200 body characters available are dropped. Hits whose matching terms lie beyond the cap are dropped as `lexical-overlap`: an accepted recall cost; raise `MEGAVIBE_POMA_MAX_CHARS` to include more. Dedup hashes the path and delivered excerpt. Without Python, recall is withheld rather than bypassing these checks. Unsupported or malformed JSON output also withholds recall (`bad-output`); there is no text-parser fallback. Searches have a five-second timeout, logged as `timeout`.

**Umbrella sessions:** `MEGAVIBE_EXTRA_AGENT_DIRS` is a colon-separated allow-list of other projects' `.agent/` directories. When scope detection resolves the search to one foreign project, recall uses its index only if allow-listed and indexed; otherwise it injects nothing. Ordinary local searches use the local index. Scope skips require positive evidence: an explicit target or a glob’s literal leading directory prefix resolves inside `.agent/` (`self-search`) or a tree with its own non-allowed `.agent/` (`foreign-repo`). Native Glob prefixes resolve against its supplied `path`; Grep and shell glob prefixes resolve against cwd. Positive globs form a union; negated globs are ignored. Basename-only globs cannot establish a forbidden scope, and a brace in a directory segment stops prefix resolution at that point (an earlier literal prefix still counts). Unresolved scopes and mixed allowed roots retain local recall rather than skipping; extra roots are not queried indiscriminately. Extension-only Glob patterns such as `**/*.json` or `*.yaml` skip as `no-query-terms`. Leading `~/` in extra-root settings expands to HOME; malformed entries are ignored individually. The reindex hook still maintains configured extra roots independently. Shell expansions and arbitrary shell programs cannot be resolved by this parser.

**Known gaps:** Scope detection is best-effort. Bash content search (opt-in) with shell pipelines or compound commands, positional glob targets, or attached option values such as `-C3` can recall local notes while searching elsewhere or inside `.agent/`. Shell redirections (`rg x .agent/ 2>/dev/null`) behave like pipelines. With `MEGAVIBE_POMA_BASH=1`, a Bash command containing `$`, a backtick or a newline is treated as a possible search and may recall irrelevant historical notes. Multi-dot Glob patterns such as `**/*.test.ts` query the middle word. Wildcards before `.agent` (such as `**/.agent/**`) are not recognized as self-search. Native calls combining `path="."` with a restricting glob prefix that points into an allow-listed foreign project use the local index (a non-allowed foreign prefix still skips as `foreign-repo`). `/tmp` and `/var/log` targets are no longer skipped merely for being in those directories. Filename-dated notes age from the date in the name even if edited later; `DECISIONS.md` and `LESSONS.md` are exempt. These limitations are accepted because all recall is framed as historical, age/lexical-gated and capped.

Decisions are logged best-effort in `.agent/LOGS/injections.jsonl`. Queries are capped at 300 characters with `...`; raw Bash commands are omitted, and `not-content-search` rows contain only the reason. Candidate diagnostics include path, score, age and outcome as space permits: each row is capped at 4096 bytes, with `truncated` marking omitted diagnostics. The log retains the last 2000 lines; queries and paths are local diagnostic data. Missing prerequisites or unwritable/busy logs can prevent logging; audit contention never cancels injection. Per-session dedup uses lock-free appends to avoid waiting, so simultaneous searches in the same session can rarely repeat a hit. No files are excluded from indexing by these injection filters.

### Self-improvement

When you correct Claude, it records the pattern in `LESSONS.md`. Before every plan, it checks its lessons to avoid repeating mistakes. Your Claude gets better at YOUR project over time.

### Safety hooks

Automatically blocks dangerous commands before they execute:
- `rm -rf /` or `rm -rf ~`
- `git push --force main`
- `git reset --hard`
- `DROP TABLE`

**Known gap.** No hook prevents deleting or moving the launch directory with `rm`, `mv`, or similar commands. The tripwire detects a missing launch directory or hooks directory after the fact. The worktree removal refusals below cover the Git and Megavibe commands.

**Guard runner detects a missing launch directory.** The five blocking PreToolUse guards, including the Write and Edit guards, run through `~/.megavibe/scripts/guard-run.sh` when installed. The runner executes an available registered hook directly. If the registered hook is missing, it uses `CLAUDE_PROJECT_DIR` as the session launch root and runs that project's executable copy if present. When `CLAUDE_PROJECT_DIR` is unset, the runner takes the root from the registered hook path. If the selected root or its `.claude/hooks` directory is gone, the runner tells you to finish and exit the session and blocks the call with status 2. If the hooks directory is intact and an individual hook is missing, the runner logs the fallback and uses the installed template copy. If no copy is executable, it exits 2. Setting `MEGAVIBE_ALLOW_MISSING_LAUNCH=1` in the hook environment allows the template fallback after the directory goes missing.

**Keep the launch worktree until the session exits.** `megavibe worktree remove` refuses a target containing the current directory or the session launch directory. The Bash guard blocks standalone `git worktree remove` from a session launched in a linked worktree, regardless of the target. `git worktree prune` is still available. Commands inside shell and `eval` bodies are outside this Bash check. Finish and exit the session, then remove the worktree from another session. A human can bypass the Bash check by setting `MEGAVIBE_ALLOW_REMOVE_LAUNCH=1` in the hook environment.

On 2026-11-25, headless Claude Code 2.1.332 started an absolute-path hook on every later Bash call after the launch directory was trashed, moved, moved and recreated empty, or removed. The hook ran from the moved path after trashing or moving, from the recreated path after recreation, and from the home directory after removal. `CLAUDE_PROJECT_DIR` retained the original path in all four cases. A relative-path hook ran after trashing or moving the directory and failed after recreation or removal. This measurement covered one version in headless mode. Interactive mode was unmeasured.

**Memory search runs against a warm daemon.** Every `poma-memory search` reloads the embedding model and re-reads every stored embedding — 0.52s, of which the search itself is under 10ms — and the recall hook runs for eligible Grep/Glob searches and, with `MEGAVIBE_POMA_BASH=1`, supported shell content searches. A `SessionStart` hook keeps one resident daemon per machine (`poma-memory serve`, unix socket, 0600) in a named tmux session, which takes the hook end-to-end from ~690ms to ~330ms; one warm process can serve each authorized project index. Find it with `tmux attach -t poma-serve`, kill it with `tmux kill-session -t poma-serve`, and it reaps itself after 30 idle minutes. Spawn outcomes land in `.agent/LOGS/poma-serve-spawn.log`. Set `MEGAVIBE_POMA_SERVE=0` to opt out. Nothing depends on it: `poma-memory search` talks to the socket when one is there and runs in-process when it is not, so a dead daemon costs speed and never correctness — the hook is byte-identical either way.

**One session per branch, without splitting the project's memory.** Several sessions in one checkout fight over the branch: one switches, another commits onto it without noticing. `megavibe worktree review` creates `../<repo>-review` on its own branch, sharing one `.git`. The part that matters is what it does *not* isolate — `.agent/` and `.claude/` are symlinked back to the main checkout, so the event log, TASKS, DECISIONS and the memory index stay one thing across every session, and every worktree runs identical hooks. A per-worktree copy would quietly split the project's memory in half. `megavibe worktree` lists them, `megavibe worktree remove <name>` takes one away and keeps the branch.

When another session is active in a Git checkout, `megavibe --parallel-branch review --no-stash` starts a parallel session without prompts. Use `--parallel-branch NAME` (or `--parallel-branch=NAME`) or set `MEGAVIBE_PARALLEL_BRANCH`. The unattended default is **not to stash**. Use `--stash` to stash tracked changes, or set `MEGAVIBE_PARALLEL_STASH` to `1`, `yes`, or `true` to stash, or `0`, `no`, or `false` to leave changes in place. Command-line options override the environment, and the last stash flag wins. Supplying only a stash choice still prompts for the branch name. These options have no effect unless another session is active in the checkout.

**Credentials never reach the logs.** `.agent/LOGS/tool-events.*.jsonl` records every tool input and response verbatim, and `.agent/events/` is committed to git — so one `env` in a Bash call used to write every exported API key to disk permanently. The `redact-secrets.sh` helper now filters all three write paths (the tool-event log, `agent-log.sh` entries, and the context watcher's own event writes): it replaces the values of environment variables that look like credentials, plus well-known token shapes (`sk-`, `ghp_`, `AIza`, `xox*-`, `glpat-`, `AKIA`, `Bearer …`), and strips the password out of any inline `user:pass@host` URL while leaving the host readable. A variable carrying a secret under a name no heuristic can recognise goes in `~/.megavibe/redact-vars`, one per line. It fails open by design — if perl is missing or the helper is not found, the log is still written unfiltered and a line lands in `~/.megavibe/hook-errors.log`, because losing a log entry is worse than failing to redact one. It is defence in depth, not a guarantee: base64, url-encoded and `\u`-escaped copies are not matched.

**Disk space.** `disk-check.sh` runs at session start, after a compaction, and (through `log-tool-event.sh`) once per 5 minutes of tool activity, and speaks up only when free space on the home or separate session-scratch volume is below the larger of 40 GB and 15 percent of the volume (`MEGAVIBE_DISK_WARN_GB` fixes the line in GB, critical below `MEGAVIBE_DISK_CRIT_GB`, default 8), listing the biggest places to look — the Trash, agent temp directories, caches and logs, `.agent/ASSETS`, `.venv`, `.worktrees`, `node_modules` — as sizes only. `scripts/disk-watch.sh watch` is a quiet Monitor loop for long jobs: it prints only when free space moves by 1 GB or crosses a threshold. At session start or after compaction, a warning includes the same boot-volume estimate as `~/.megavibe/scripts/disk-watch.sh footprint`. It reports allocated space in the current user's Claude scratch roots, attributable shared temp entries, and Git-registered worktrees under Megavibe's worktrees directory. The line says how this compares with total used space and flags incomplete scans. The footprint scan has a three-second deadline. These checks only report. `MEGAVIBE_DISK_WATCH=0` switches the hook off.

**Session scratch: produce less, clean up at the end of every unit of work.** Three days of use filled a boot disk with 29 GB of session scratch, most of it whole-repository copies made for readers. `TMPDIR=<scratchpad> ~/.megavibe/scripts/review-copy.sh make [PATH...]` replaces `cp -R`: it writes the working-tree files git lists for the repository (edits and untracked files included) without `.git`, ignored dependencies, build output or symlinks, nothing over 2 MB, optionally only the PATHs under review; a diff is handed over separately with `git diff`. Measured on real checkouts the copy is 1.0x to 5x smaller than the directory (a 1.5 GB working directory became 0.32 GB; a 415 MB one 88 MB), and a few hundred KB when only the files under review are named. `review-copy.sh remove DIR` removes a copy for real, write-protected ones included (the copies `claude-review.sh` makes are read-only, which makes a delete from the Trash fail with `Permission denied`), and `list` shows what is left; give `list` and `remove` the same TMPDIR. `make` costs a few milliseconds per file (about 30 s for 10,000 files), so on a very large repository name the PATHs under review. The protocol says a round is not done while its copies exist.

The scratch budget measures the current session's directories across all known scratch roots, including its short `TMPDIR`, plus session-owned entries in shared temp. In shared temp it counts review copies marked with the session ID, reviewer scratch created after the session-start stamp with a recorded dead PID and no remaining reviewer process, and entries the session registered. Use the session scratchpad for large items you place explicitly. Register items you create directly under the shared temp base with `~/.megavibe/scripts/scratch-own.sh register PATH` or `scratch-own.sh register SID PATH...`. Registration accepts existing direct children of the temp base created after the stamp. Replacing an entry requires a new registration, and symlinks are rejected. Other temp usage is reported by size and age.

The SessionStart hook exports `TMPDIR=<scratch root>/t/<first 8 characters of the session ID>` for Bash calls through `CLAUDE_ENV_FILE`. The short path leaves room for Unix socket names and the private directory carries a `.sid` marker with the full session ID. Sourcing the export recreates a missing directory with mode 700 and skips creation when the path is a symlink. The hook skips the export if the path is too long, another session owns the prefix, the env file is unavailable, or `TMPDIR` is already set to a non-default location. Set `MEGAVIBE_SESSION_TMPDIR=0` to opt out. Pytest's default base follows this export. Hardcoded `/tmp` paths, consumers of `getconf DARWIN_USER_TEMP_DIR`, and tool caches with their own paths follow their own settings.

`MEGAVIBE_SCRATCH_BUDGET_GB` defaults to 2 GiB. The periodic check runs every five minutes of tool activity and reports the first overage and each additional GiB. While disk space is below the warning threshold, it also names the three largest other temp entries with their sizes and ages. The main thread's Stop check can block once when a complete measurement exceeds the budget and again after another 256 MiB of growth. Unknown measurements, timeouts, partial totals, and other temp usage allow Stop to proceed. A budget of zero disables the budget, and `MEGAVIBE_DISK_WATCH=0` disables the disk and scratch checks.

The disk and budget checks measure usage. Run `scratch-own.sh list SID` to inspect session-owned temp entries and `scratch-own.sh clean-unit SID` after a unit finishes to remove eligible entries directly. The SessionEnd hook runs `clean-end SID`, which removes eligible attributed temp entries and sweeps the session’s own scratchpad under each known session root. It keeps entries with changes in the last hour and keeps any scratchpad entry containing a file named `.keep`, including a top-level `.keep`. It removes the session directory when it is empty. Attributed cleanup preserves active reviewer scratch. Both cleanup commands recognize the short temp directory by its full session marker and respect `.keep` within it. `clean-unit` clears eligible contents while preserving the short directory and its `.sid` marker. `clean-end` removes the whole short directory when it has no changes from the last hour and contains no protected reviewer scratch.

On startup and resume, a six-second sweep removes scratch for ended sessions when every tree entry is older than `MEGAVIBE_SCRATCH_ORPHAN_HOURS` (24 by default, 0 disables it). It preserves the current session and other sessions whose records identify a live PID with the matching process start time, even if they have been idle longer than the cutoff. SessionStart makes a best-effort record of absolute custom `CLAUDE_CONFIG_DIR` paths in `~/.megavibe/claude-config-dirs` (up to 256 lines or 64 KiB) so sweeps from other sessions can read their records. Damaged records, missing or unreadable registered config or sessions directories, and an inconclusive process scan suspend session scratch cleanup for that sweep. A two-second process scan checks that every running process owned by the current user whose command basename is exactly `claude` has a matching live session record. An unmatched process suspends session scratch cleanup, which protects sessions started in undiscovered custom config directories before the registration hook was installed. Headless `claude -p` workers without a session record also cause the session sweep to skip. The next session start retries. Installs that run under another process name, such as `node`, get no additional protection from this check. It skips symlinked roots, foreign-owned trees, and trees with `.keep`. Directories outside the harness project-slug layout and non-UUID session directories within project slugs are reported by size when you run `scratch-own.sh sweep-orphans SID` directly. The sweep also removes old, unopened numbered runs under the system temp's `pytest-of-<user>` directory. These are test fixtures by construction. A missing or inconclusive `lsof` check leaves the run in place.

**`kubectl` and `gcloud` never ask a human to log in.** Many orgs enforce a re-auth policy — Google Cloud RAPT, AWS SSO, an Okta-fronted OIDC provider — that refuses to refresh credentials outside an interactive terminal, so an agent session dies hourly with something like `Reauthentication failed. cannot prompt during non-interactive execution`. The usual answer is a small keeper script that mints a short-lived token to a file, and it works right up until the agent forgets the keeper exists and tells you to go log in instead. (Measured across two real setups: 19 such asks in 9 projects before this hook, and — because the hook originally covered only `kubectl` — another 74 `gcloud auth login` suggestions in a single project afterwards, with a usable token sitting in the keeper's file the whole time.) Point `cloud-token.sh` at your keeper and it stops being something anyone has to remember: on any Bash command that mentions `kubectl`, `gcloud`, `kubeseal` or `helm`, it runs the keeper when the token file is missing or stale, then puts one line in front of the command, `export CLOUDSDK_AUTH_ACCESS_TOKEN_FILE='<token file>'`. gcloud reads that property directly, and kubectl on GKE reaches it through `gke-gcloud-auth-plugin`, which asks gcloud for its token; a Google `ya29.` access token serves both. The command itself is never changed, so heredocs, quotes and comments are safe. A kubectl started by a script or `bash -c` is covered when the command line names one of the tools; a script whose command line names none of them, `sudo`, `env -i` and `ssh` are not, and only GKE credentials go through gcloud (EKS/OIDC contexts and other tools' application-default credentials are untouched). Configure it in `~/.megavibe/personal/cloud-token.conf` (or the same three environment variables) with `KUBE_TOKEN_FILE`, `KUBE_TOKEN_KEEPER` and optionally `KUBE_TOKEN_MAX_AGE` (default 50 min); with none of them set the hook is inert, so it costs nothing if you use neither tool. Only the token file's path is exported, never the token, so it does not enter a shell variable, the transcript or the model's context. A command that contains the word `gcloud` together with `auth`, `config`, `components` or `init` anywhere, or that selects its own identity (`--account`, `--configuration`, `--credential-file-override` with gcloud, or any of `CLOUDSDK_CORE_ACCOUNT`, `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE`, `CLOUDSDK_ACTIVE_CONFIG_NAME`, `CLOUDSDK_CONFIG`, `CLOUDSDK_AUTH_ACCESS_TOKEN`), gets no token: with the property set gcloud uses the token file instead of the stored accounts, so a login would be shadowed by the token it replaces and `auth revoke` or `print-identity-token` would answer for the wrong identity. The check is word co-occurrence after deleting quotes and backslashes, not gcloud's grammar, so it errs towards skipping (no token, the behaviour before this hook); when a skipped command also runs kubectl, helm or kubeseal, the agent is told to run the cluster command as its own call. With gcloud in the command, `$'…'`/`$"…"` quoting, `--flags-file` and impersonation (`--impersonate-service-account`, `CLOUDSDK_AUTH_IMPERSONATE_SERVICE_ACCOUNT`) also skip; every skip, and a keeper that failed to refresh the token, tells the agent why. The guard is against honest mistakes, not a command built to get past it: any command the agent runs can read the token file directly, so a group or the gcloud name assembled from variables, globs or expansions crosses no boundary and is not recognised. Commands that need a stored service-account key, such as `gcloud storage sign-url`, still see the token instead. An explicit `--token` or `--access-token-file` wins over the property. If the keeper fails and the token is still stale, nothing is handed over. (An earlier version rewrote each `kubectl`/`gcloud` word to carry a token flag. That needs a shell parser, and it rewrote heredoc bodies being written to files.)

**Kill guard.** `block-dangerous-bash.sh` also refuses `pkill`, `killall`, `tmux kill-server|kill-session|kill-window|kill-pane` and `launchctl bootout|unload|remove|stop|kill|bootstrap|disable|kickstart -k` (a reviewer's `pkill` took down every tmux-hosted session on 2026-10-15). It parses the command with `shlex` (wrappers like `sudo -u x`, `env`, `bash -c` are followed; quoted text and heredoc bodies are not commands). One launchctl form passes, because it stops nothing: `launchctl bootstrap gui/<your uid> ~/Library/LaunchAgents/<name>.plist` as the whole command (a literal uid, `~` or `$HOME` in the path, one plist directly in your own LaunchAgents folder, no symlink out of it, output only to `/dev/null` or a numbered stream such as `2>&1`; no wrapper, no second command, no substitution). The loaded agent may start a program of its own (`RunAtLoad`), as `launchctl load` already could. `env -S` carrying launchctl stays blocked. Command substitutions (`$( )`, backticks, `<( )`, inside double quotes too), `eval` and `find -exec` are checked as commands. Text the tokenizer cannot read fails CLOSED: a kill verb anywhere in it blocks (2026-11-23: nested quotes inside `"$( )"` broke the tokenizer, the guard passed `tmux kill-server`, and the live tmux server died). A check that cannot run (a broken `python3`) blocks only when the text visibly names a kill verb. Subshells (`(cd x && ls); tmux kill-server`) and escaped quotes (`"a\""`) no longer hide the next command. A tmux kill verb passes only with `-L` and a literal name other than `default` that is not the socket `$TMUX` names nor a symlink to a `default` socket (compared case-insensitively). Any `-S`, a name built by a substitution or a variable, a `TMUX_TMPDIR` that is not a plain literal, a user switch (`sudo`) or a link made in the same command (`ln`) keeps the block; those words are read anywhere in the command text, so prose that mentions them also withholds the allowance. The guard cannot tell who started a named server, so `-L work` also reaches a long-lived server of yours by that name; only `default` and the `$TMUX` socket are protected. Such a selector is meant for a server the caller started: inside tmux, `$TMUX` overrides `TMUX_TMPDIR`, so only `-L`/`-S` isolate (see process-discipline). Not caught (as on main before this change): `kill $(pgrep …)`; tmux verb prefixes and aliases (`kill-serv`, `killp`), `;`-separated tmux command sequences, `tmux -c`, and shell text run by tmux verbs (`new … 'pkill x'`, `run-shell`, `send-keys`, `if-shell`); `trap` handlers, `function NAME { }`, wrappers outside its list (`setsid`, `watch`, `caffeinate`, `coproc`, `su -c`), `env -S`; heredocs and here-strings fed to a shell (`bash <<EOF`, `bash <<<`); redirections before the command word (`>/dev/null pkill x`); in the kubectl exec guard, substitutions inside a `bash -c` or `eval` body, the wrappers `timeout`, `xargs`, `eval` and `find -exec`, and an exec example inside a heredoc body is still read as a command (as before); a `-L` name built in a loop (`mvt$i`) keeps the block, so unroll it to literals; a word split by quotes (`"tm"ux`); `$'…'` quoting, nested escaped backticks, brace expansion, command names built at runtime, interpreters. Kill only a PID you started (`$!`). Tests: `/bin/bash tests/kill-guard.test.sh`. Escape hatch for a human decision: `MEGAVIBE_ALLOW_KILL=1`.

**Pipe-before-push guard.** A formatter at the end of a pipeline hides the exit status of what it formats: in `make test | tail -5 && git push` the `&&` tests `tail`, so failing tests still push. `block-dangerous-bash.sh` therefore refuses `X | F && git push`, `X | F && git commit` and `X | F && gh pr merge` (F one of `tail`, `head`, `grep`, `sed`, `awk`, `cut`, `sort`, `uniq`, `wc`, `tee`, `jq`, `rg`, `tr`, `cat`; also through `git -C dir` and `cd dir &&` steps). Three ways through: `set -o pipefail` earlier in the same call (`set -o pipefail; make test | tail -5 && git push`); a `PIPESTATUS` check between the pipeline and git (`make test | tail -5 && [ "${PIPESTATUS[0]}" = 0 ] && git push`); or a dry run, when every push or commit in that `&&` chain is one (`--dry-run`, and `-n` for push only, since `commit -n` skips hooks). A `;` instead of `&&` does not trigger it: there the command does not depend on the pipeline. It costs no extra process unless the command contains `|` and one of push, commit or merge, and then one `perl` call. Not covered: global options before the verb (`git -c k=v push`, `git --no-pager push`), wrappers (`env git push`, `command git push`), machines without `perl` (the guard is skipped), a pipeline inside a compound command (`if make test | tail -5; then git push; fi`), any text naming `PIPESTATUS` between the pipeline and git, which counts as the check even when it checks nothing (`echo PIPESTATUS`), and every chain after the first that matches: only that one is judged, so `make test | tail -5 && git push --dry-run; make test | tail -5 && git push` passes. Blocked by design: `grep -q` as the condition (`git diff | grep -q x && git commit`), because the guard cannot tell a test from a formatter; run the check in its own call or set pipefail. Falsely blocked: an unquoted `$(… | wc -l)` before `&& git commit`; quote the substitution (`"$(ls | wc -l)"`), which the guard reads as text.

**Cheap amass pass.** `scripts/amass.sh run --out DIR --change "…" FILE…` inlines the files into one prompt and sends it to many headless one-shot calls (`claude -p --model haiku`, no tools, no user or project settings, no MCP; one lens per prompt, up to 150 KB of input), then `amass.sh dedupe --out DIR` clusters the lists. Claude workers have no tools; with `--provider auto` or `codex`, Codex workers run in Codex's read-only sandbox (no writes, no network) and can read local files, so they are not tool-less, and text injected into untrusted inlined code could steer them to read files on the machine. It costs cents, produces leads rather than verdicts and is not itself a review; the review tiers are unchanged, but a sweep must now precede a reader round: `codex-review.sh` and `claude-review.sh --as-reviewer` refuse (exit 6) without an `amass.sh run` for this directory and, in git, this content (a tree hash of the tracked files) in the last 120 minutes, or a `--no-amass` waiver for that call: `oversize` or `prose`, both checked against the files, or `hotfix`, shown as an owed sweep at session start and in `tick.sh` (`scripts/amass-gate.sh`). An Agent-tool subagent starts with about 93K tokens of inherited context in a project with heavy instructions, which is why a headless call is about 25-70x cheaper for bounded read-only work. Measurements and limits: `README-amass.md`.

**Claude reader, the counterpart of `codex-review.sh`.** `scripts/claude-review.sh [--as-reviewer] --prompt-file F [--model sonnet] [--tools exec|read|none] FILE…` is one lean headless worker call on the Claude subscription with the same interface: files appended as `===== path =====` blocks, a throwaway scratch directory (deleted on exit), `--out`, `--timeout` (exit 124). With `--tools exec` (the default under `--as-reviewer`) it can run things, and on macOS the process runs under a seatbelt profile that denies every file write except the scratch directory and claude's own state, with the guard hooks registered and no project rules loaded; it refuses to run `exec` where it cannot confine writes. In `exec` mode the worker and every command it runs see `MEGAVIBE_SANDBOX=1`, so a project can skip what cannot work in a sandbox (for example a GUI app that would abort and show a crash dialog). It is a hint, not a guarantee (anything the worker runs can unset it), so use it only to skip what cannot run there, never to relax a check. The network is not confined (claude needs it). It refuses anything but a claude.ai subscription login. The report is the worker's text after its last tool call (plus its final result, after `---`, when that differs), so a report written before a later tool call keeps only what follows that call. Which provider takes a unit of work is the continuous allocation in `.claude/rules/delegation.md`, "Both providers, in every shape".

**Disk and worktree audit.** Run `~/.megavibe/scripts/worktrees-audit.sh audit` first when disk is low; `scratch` and `caches` also report sizes without deleting. Both `audit` and `remove-safe` need network access to verify remote state: they fetch and prune each remote's branch refs and ask the server for its default branch, with a 45-second limit per network command. Fetch only updates remote-tracking refs, not local branches, tags or worktree files. `--offline` skips these requests and keeps every worktree that needs remote verification. Review `remove-safe --dry-run` before `remove-safe`: removal is limited to clean, fully pushed, unlocked worktrees merged into the verified default branch (origin's when present, otherwise the first remote's), or detached at a verified remote-reachable commit. The main worktree and any worktree containing the invocation directory are protected.

`KEEP` reasons explain why a worktree stays: `remote-unverified` means offline, missing or failed remote verification; `git-lock` means a Git transaction lock exists or the bounded lock scan could not verify the metadata; `pending-operation` means Git has unfinished work (including autostashes); `submodule` means any indexed gitlink, initialized or not; `parked-branch` means a named branch is not merged into the default; `unpushed` means commits lack verified remote reachability; `grafts` and `replace-refs` mean the repository has `info/grafts` or replace refs, which can make a local-only commit look reachable, so every worktree of that repository stays (the tool also ignores inherited `GIT_*` overrides such as `GIT_GRAFT_FILE`, `GIT_DIR` and `GIT_CONFIG_PARAMETERS`). Dirty, locked, hidden-index-state, changed and unreadable states also stay put. The tool never removes a worktree it can detect as dirty, unpushed, locked, mid-operation, or unverifiable. It checks local state again immediately before acting, including transaction locks in the worktree Git directory and common metadata/refs. **Known limit: verification and removal are not atomic.** A process writing into a worktree in the short window between the final check and removal is not protected: `git worktree remove` without `--force` does not protect unpushed commits or ignored files created in that window. Only remove worktrees nobody is using; this is why `remove-safe` prints the list before acting. Before each removal, the tool writes and flushes a JSON intent (`time`, `repo` common Git directory, `path`, `branch`, `sha`, `size` in KiB, `status: intent`) to `${MEGAVIBE_HOME:-$HOME/.megavibe}/worktrees-audit-removals.jsonl`, with mode 0600 where possible, and appends an outcome with `status: removed` or `status: refused` afterward. Successful removals also invoke the project's agent-log hook when present. A failed intent write keeps that worktree with `log-write-failed`; an unwritable log destination prevents all removals. An outcome write failure stops further removals, leaving the intent for investigation. `git worktree remove` frees space immediately and bypasses the Trash; `rm`-style deletes routed through rm-to-trash remain recoverable in the Trash until the user empties it.

**Deletions go to the Trash.** On a Mac with `rmtrash` installed (`setup.sh` installs it where Homebrew exists), the `rm-to-trash.sh` hook rewrites every `rm …` Claude runs into `rmtrash …` before it executes — same flags, but the files land in `~/.Trash` instead of disappearing. A wrong delete becomes a drag out of the Trash. Only `rm` in command position is touched — including inside `$( )`, `find -exec`, `xargs {}` and after a plain `sudo`; never text inside quotes, heredoc bodies, comments, `case` patterns or a `rm()` definition; a quoted `bash -c "rm …"` body is therefore refused by `block-dangerous-bash.sh` (below) rather than run as a real `rm`. (A wrapper with its own options — `sudo -u bob rm`, `nice -n 5 rm`, `timeout 5 rm`, `env -u X rm` — is followed too: per-wrapper option tables find the command it actually runs, so `sudo -u bob rm` is rewritten and `sudo git rm` is not. Redirects, including before the command, and here-strings do not change which word is the command; an `rm` run by `xargs`, or with a command substitution in its arguments, always goes to the Trash because its operands cannot be seen. Commands inside `$( )`/backticks are rewritten even in a double-quoted string or an unquoted heredoc body, where bash runs them.) It rewrites the command line Claude runs, not the inside of a script it invokes. Every target goes to the Trash, temp directories and `node_modules` included: Claude scratchpads live under `/private/tmp` and hold days of work, and a glob there destroyed finished work for good on 2026-10-26. `rm -W` (undelete) stays real; `rm -P` (overwrite), `shred` and `srm` are refused by `block-dangerous-bash.sh`. `MEGAVIBE_RM_SCRATCH_REAL=1` in Claude Code's environment restores the old behaviour, where targets all under the temp dirs (`/tmp`, `/private/tmp`, the per-user `/var/folders/…/T`, a well-formed `$TMPDIR`) or `node_modules` keep real `rm` so scratch data frees disk at once; the rest of this paragraph describes that mode. Targets are resolved first — `..`, symlinks and a leading `cd <dir>` are followed, the path must be inside the temp dir both as written and after symlink resolution — and the hook only reasons about a command that is nothing but an optional leading `cd` plus `rm` segments joined by `&&`/`;`. Anything it cannot prove (a relative path without that shape, `~`, `$HOME`, other variables, braces, a glob through a symlink, a command substitution among the arguments, an `rm` run by `xargs`) goes to the Trash; an absolute scratch target stays real even with redirects after it (`rm -rf /tmp/x 2>/dev/null`) or in a compound line. Known trade-off: arithmetic that uses a variable literally named `rm` with a bitwise operator or an operator hidden in an expansion (`$((rm $op 1))`) may be rewritten, which makes bash report a syntax error (never a deleted file), because a static check cannot tell it from a nested command list. Known gap, same as before this resolution existed: a symlink created earlier in the same command line can redirect an absolute `/tmp` path. If the analysis itself crashes, a crude fallback rewrites every `rm` in command position (separators, keywords, assignments, `find -exec`, wrapper chains; `git rm`/`docker rm`/`echo rm` are left alone, and a deletion carrying `-P`/`-W` stays real per command) to `rmtrash` — over-eager on purpose, logged in `~/.megavibe/hook-errors.log` — rather than leaving `rm` real. A shell alias only covers interactive shells; the hook covers the command line Claude runs directly. There is no escape hatch for `rm`: `\rm`, `/bin/rm` and `/usr/bin/rm` are rewritten too, deliberately. Making something unrecoverable is the user's call: `shred`, `srm` and `rm -P` are refused unless they set `MEGAVIBE_ALLOW_REAL_DELETE=1`. Note the tradeoff: a large `rm -rf dist` now fills `~/.Trash` rather than freeing the space — reclaiming it is the user's call, in Finder or through the Trash greenlight below, informed by the Trash review. `block-dangerous-bash.sh` refuses any attempt by Claude to empty the Trash or delete from it, except the one script that sits behind a permission prompt (see "Trash greenlight") (Finder `empty` via `osascript`, `rm`/`find -delete`/`rsync --delete` on `~/.Trash`, `trash --empty`), because the Trash is the only undo an agent's deletes have; an agent "freeing space" emptied one on 2026-09-30. It parses the command text (`shlex`, so quoted prose such as a commit message is not a command), which means it allows what it does not recognise: a script file, an interpreter one-liner that builds the delete call from pieces (`python3 -c 'getattr(os, "un" + "link")(…)'`), a runtime-assembled or obfuscated path (`T=~/.Tr; T=${T}ash`, `~/.Tras*`, `~/.Tr$'a'sh`), `tar`/`zip` deleters and other exotic forms still get through, and prose inside a heredoc that feeds a shell or interpreter is blocked. The gate in front of the greenlight script adds one deliberate over-block: any Bash text containing `trash-e` is refused (`git add scripts/trash-empty.sh`, `bash -n`, `grep`, a commit message naming it); use the Read and Grep tools, `git add scripts/`, and `git commit -F` (see "Trash greenlight" below). Three independent review rounds each found new bypasses in the earlier versions, so treat it as a net with holes, not a wall. Case variants (`.TRASH`) are covered because APFS is case-insensitive. Without `python3` a cruder regex applies. Any miss is a permanent delete when `MEGAVIBE_RM_SCRATCH_REAL=1` is set, since that mode leaves `rm` on a `.Trash` target real. Deleted files land in the boot disk's `~/.Trash`, or the volume's own `.Trashes` off other disks.

**Deleting from code is blocked, too.** `rm-to-trash.sh` only sees `rm`, so `block-dangerous-bash.sh` refuses the other ways an agent reaches for a real delete: an interpreter (`python`, `node`, `perl`, `ruby`, …) whose inline code or feeding heredoc calls `shutil.rmtree`, `os.remove`/`unlink`, `fs.rmSync`, `FileUtils.rm`, `unlink` or runs `rm` as a subprocess (where it is not rewritten), and `find -delete`, `unlink` and `git clean -f` as commands. The fix is always the same: collect the paths and `rm` them, or call `~/.megavibe/scripts/trash.sh` from the code (a bare `rmtrash` skips the ledger). It reads the command TEXT coarsely and blocks on co-occurrence: an interpreter (`python`, `node`, `perl`, `ruby`, `awk`, …) that runs, plus a deletion API anywhere in the text or a subprocess string that runs `rm`, `find -delete`, `unlink`, `shred` or `git clean -f`; a shell, `eval`, `trap`, `env -S`, `parallel` or `awk` that runs, plus `rm` inside quoted text or a heredoc it consumes, or `rm` text piped into a shell; `rm` spelled so `rm-to-trash.sh` cannot see it (`"rm"`, `\rm`, `RM=rm; $RM`, `$(which rm)`); `unlink`, `shred` or `srm` fed by `xargs`/`parallel`, and `rm` run by `fd -x`; `rm` split by a line continuation; and `find -delete`, `unlink`, `shred`, `srm`, `rm -P`, `rimraf`, `git rm -f` and any `git clean` but a dry run (`-n`), `git worktree remove` with `--force`/`-f` (or an abbreviation such as `--for`), read as tokens so global options (`-C`, `--git-dir`, …), quoting and interpreter argument lists are followed, in command position (after keywords, wrappers with options, `VAR=` and redirections, inside `$( )` even in double quotes). Over-blocking it accepts: an interpreter name that is only an argument (`brew unlink node@18`) counts as running it, and a deletion phrase quoted in the same call as a shell or interpreter (`python3 -m pytest -q && git commit -m "use os.remove less"`, `docker run -e MODE="rm" img`) is refused; run the commit, `gh` call or `grep` as its own Bash call, or pass the text with `-F`/`--body-file`. Comments are ignored for shell commands (text after a `#` on a line that runs an interpreter still counts), and quoted options (`'-delete'`) still count. A heredoc counts only when a shell or interpreter consumes it (or its line ends in a pipe), and only when a later line closes it, so a commit message or note written through `cat <<'EOF'` passes; a command that runs a shell or interpreter and merely mentions these calls in quoted text is refused (write such text to a file with the Write tool, since a heredoc that runs would trip it too, and pass the file, e.g. `git commit -F`). It is active only where `rmtrash` is on PATH, the same condition `rm-to-trash.sh` uses: without it `rm` deletes for real anyway, and blocking the other forms would only push agents towards that. A pattern that runs longer than two seconds blocks the command rather than letting it through. `\rm` with one leading backslash is rewritten like `rm`; `trash.sh` falls back to plain `rmtrash` when `python3` itself is broken. Plain `git worktree remove` also deletes the worktree's ignored files (`.env`, `node_modules`) for good and is refused by git itself while the worktree has modified or untracked files, so check `git status --porcelain --ignored` (plain `git status` hides ignored files); the recoverable route is `rm -r <worktree>`, which goes to the Trash, then `git worktree prune`. Review rounds kept finding spellings a shell parser here missed, which is why it is coarse; it is still a net, not a wall. Not covered: a script FILE an interpreter or shell runs; code assembled at runtime; `docker run … rm` inside a container; `script`, `flock`, `watch` or `source <(…)` running `rm`; `rsync --delete`/`--remove-source-files`, `tar --remove-files`, `zip -m`; build-tool cleans (`make clean`, `npm run clean`, `cargo clean`, `mvn clean`); options or command words quoted in pieces (`-de"lete"`, `git work"tree" remove`), a `$( )` inside a forced `git worktree remove`'s own arguments, commands inside a `function name { … }` body. `megavibe worktree remove` itself forces the removal after its own check for deliverables, so it deletes ignored files too and `$'...'` quoting; a deleter in quotes after `find -exec` or `fd -x`; a `#` that bash does not treat as a comment (after an escaped space or a `)`, at the start of a continuation line) is read as one and hides the rest of its line; dozens of `xargs` options in one command trip the two-second limit and are blocked; a quoted `rm` behind a wrapper option that takes a value (`sudo -u bob "rm"`, `nice -n 5 "rm"`); a nested quote inside a double-quoted `$( )` (`"$(printf '%s' '$(which rm)')"` is refused although it only prints); a backtick after an even run of backslashes (`"\\`cmd`"`); interpreters outside the list (`ipython`, `ts-node`/`tsx`, `Rscript`, `julia`, `uv run -`) and the wrappers `unbuffer`, `chronic`, `busybox`, `ssh host`, `su -c`; `rmdir`; overwriting a file with `mv`/`cp`/`>`, and truncation; anything run outside the Bash tool.

**A delete on a remote host goes to the permission prompt.** There is no Trash on the other side of `ssh`, and until 2026-11-15 both delete guards treated the quoted remote command as an opaque argument: an agent ran an approved log purge over ssh, appended an `rm -f` of a neighbouring file nobody had approved, and nothing fired. `block-dangerous-bash.sh` now reads the remote command (quoted or not, through `sh -c`, `eval`, `trap`, `xargs`, `find -exec`/`-delete`, `$( )`, interpreter one-liners, `git clean`/`git worktree remove`/`git rm -f`, `tar --remove-files`, a nested `ssh`), a script sent to a remote shell on stdin (a heredoc, a here-string, `< script.sh`, `cat script.sh |`, `echo … |`, `printf … |`), `sftp`/`lftp` command text and batch files, and `rsync` with a `--delete…` option towards a remote destination or `--remove-source-files` from a remote source (not on a dry run). When it finds a delete it returns `permissionDecision: "ask"` with the host and every deleted path in the reason, so the human compares them with what they approved, and a path added to an approved command is visible as its own line. The parse behind those lines is lossy, so the reason also carries the whole remote command or script as written (for a piped `echo`/`printf`, the command that produces it), and a text too long to show says in capitals that it is incomplete. Under the parser sits a coarse backstop: where it finds nothing in a text that runs remotely, a pattern still looks for `rm`, `rmdir`, `unlink`, `shred` or `srm` in command position (after a separator, behind `sudo`, `xargs`, `env` and similar with their options, after `find -exec`), for the same words with a path-like operand behind a command that is not known to take such words as data (`chroot DIR rm -rf x`; `grep`, `echo`, `docker`, `git` and similar are exempt), and for `find … -delete`, and asks with the text shown; four review rounds each found a spelling the parser missed, so the prompt does not depend on the parser being complete. The price is an occasional prompt on text that only looks like a command (`echo "a; rm b"`). A relative script path is read from where the shell then is (a literal `cd dir &&` before it is followed; after `cd "$VAR"`, `cd -` or `pushd` it is not read and the call is asked about). The local real-delete check (previous paragraph) still reads the whole command as before, so a form it already refused stays refused rather than asked about: a shell or interpreter word outside the quotes (`ssh host bash -s <<EOF … rm …`, `echo 'rm x' | ssh host sh`), an unquoted remote `find -delete`, an `rm` directly before the closing quote after `xargs`. The block message then names the form that does reach the prompt: a plain `rm` or `find … -exec rm {} +` in a single-quoted `ssh` command of its own. Measured 2026-11-15 on Claude Code headless with Bash allow-listed, in `default`, `dontAsk` and `bypassPermissions`: the call does not run and the reason reaches the agent. In an interactive session the hooks documentation says the user is prompted; that was not measured here, bypass mode included. The reason tells a denied agent what to do instead: move the files into a dated quarantine folder on that host (`mv` is not a delete and passes), or name the exact paths to the user. A stdin script the guard cannot read (a variable path, a missing file, another command's output) is asked about as well. It runs with or without `rmtrash`, and there is deliberately no environment switch and no inline acknowledgement: `MEGAVIBE_ALLOW_REAL_DELETE=1` does not open it. Without `python3`, or when the check itself fails to run, a crude text match asks instead. Not covered: a script that already lives on the remote host, `kubectl exec`/`docker exec` payloads, `scp`, `mv` and redirects that overwrite, truncation, database statements, `rclone` and other clients, a command line assembled at runtime; a net for honest mistakes, like the guards above. Tests: `/bin/bash tests/remote-delete.test.sh`.

**A push to a public repository is checked first.** On 2026-11-21 a session pushed a branch with internal material to a repository that turned out to be public; it stayed reachable for about 50 minutes. `block-public-push.sh` (PreToolUse, runs in every project) fires on `git push` (shlex-parsed like the kill guard: `bash -c`, `sudo`, `env X=1`, `git -C dir`, `cd dir && git push`), `gh pr create`, `gh repo create --public` and `gh repo edit --visibility public`. It resolves the push URL (`pushurl`, `insteadOf`, the branch's remote, an ssh alias via the HostName lines of `~/.ssh/config`, read as text), asks `gh repo view --json visibility` (cached 5 minutes per repo, unknown results never cached) and acts on the answer: a PRIVATE or INTERNAL target passes with no scan; a PUBLIC target has its outgoing commits (`git rev-list <src> --not --remotes=<remote>`, so a new branch yields every commit the remote lacks; at most 500 commits and 8 MB of diff) scanned for home paths (`/Users/<name>/`, the real login name always; placeholders such as `/Users/you/` pass), private keys and token shapes (a line containing `example`/`placeholder`/`xxx` is skipped, the convention of `scripts/leak-scan.sh`; a line carrying the uppercase marker `EXAMPLE` declares itself a fixture and is exempt from the home-path and email patterns as well, so only the denylist applies to it), email addresses (except the commits' own authors, trailer lines, noreply, `example.com`/`.org`/`.net` and the reserved `.example`/`.invalid`/`.test` domains, and `~/.megavibe/personal/public-push.allow-email`) and your own denylist `~/.megavibe/personal/public-push.deny` (outside every repo; one entry per line, `#` comments, case-insensitive literal text or `/regex/`; customer names, host names, internal terms; example entries `ACME Corp`, `/prod-db-[0-9]+/`). Hits go to the permission prompt (`permissionDecision: "ask"`, honoured under bypass and forwarded to the phone, like the remote-delete guard) with each hit named by file and line and its value truncated (secrets to four characters). A clean push to a public repository **on your known-public list** passes silently; a public repository that is not on `~/.megavibe/personal/public-push.known-public` (one `host/owner/repo` glob per line, e.g. `github.com/you/yourtool`) asks whatever the scan says, because the incident was a repository nobody knew was public and its content matched no pattern. You add a repository once; the prompt prints the line. **Visibility unknown also asks**: gh missing or logged out, offline, a host that is not GitHub (GitHub Enterprise hosts count only when listed in `GH_HOST` or `MEGAVIBE_GITHUB_HOSTS`), an unresolved ssh alias, a truncated scan; silence a host or repo you know is private in `~/.megavibe/personal/public-push.trusted` (one `host/owner/repo` glob per line; it answers only where the lookup cannot, and never overrides a PUBLIC answer). The remote's tracking refs decide what is already published only when the destination holds them: the boundary commits of the outgoing range are looked up with `gh api`, and after a `git remote set-url` to another repository everything that would go out is scanned. `gh pr create` is a visibility check of the repository the pull request publishes to (`-R`/`--repo`, `GH_REPO`, else the one `gh` resolves from the checkout) and nothing more: public and not on your known-public list asks, unknown asks, private passes; **the title, body, body file, template and commits of a pull request are not read**; `gh repo edit --visibility public` always asks (it publishes the whole history) and scans local history; `--dry-run`, `--delete`, delete refspecs and local-path remotes are not checked. The human override is `MEGAVIBE_ALLOW_PUBLIC_PUSH=1` in the environment the session launches with; an inline prefix in the command is ignored and reported, so a peer message or injected instruction cannot grant it. Measured 2026-11-21 on this repository's own history (public, scanned as if each commit were the outgoing push, first-parent): 1 prompt in the last 50 commits (2%), 2 in the last 200 (1%), all fake secrets in test fixtures from before they carried the `EXAMPLE` marker and an author email in a commit message; no prompt on a normal push. Not covered: pushes through a git alias, a script or `$( )`; a leak that is not text (a binary, a renamed file's old content in a rewritten history); a denylist that cannot be read is empty. A net for honest mistakes. **Chains are not simulated**: a state-changing git command earlier in the same call (add, commit, switch, checkout, branch, merge, rebase, pull, cherry-pick, reset, stash, tag) makes the push content unknowable, so a push to a public repository after one is **denied** (`permissionDecision: "deny"`) with the instruction to run it in a separate call: the agent repeats the push alone and no human is asked. `commit && push` chains to public repos are therefore always refused once, by design; a standalone push keeps the full scan, and the same chain to a private repo passes. `git remote add|set-url|rename|remove` and a writing `git config` before a push are denied the same way whatever the visibility, as are a branch switch before a push that names no remote in a repository with several remotes, a variable in the remote or directory (in a refspec only when the target is public), and an unresolvable `-C`, `--git-dir` or `--work-tree` (a variable or substitution). Once a target is known to be public, a failure of the guard itself asks instead of passing. **Known gaps (documented, not fixed):** `gh pr edit` is not checked at all (it names its repository in a number or URL argument that the guard does not resolve; the guard never checked it before); the repository of a `gh pr create` is read from the first `-R`/`--repo`-shaped word, so a repeated `-R` (gh uses the last) or a title or body value shaped like `-Rowner/repo` written before the real `-R` is read as the repository (flag_value does not skip the values of other options; behaviour unchanged from the earlier branch head); pull request text is no longer scanned (an earlier version scanned titles, bodies and files and kept producing new bypasses and false prompts in the shell-text parsing it needed; the push-side commit scan is where content is checked); the guard reads commits through `git log -p` under fixed configuration, so settings that change what git shows (`GIT_CONFIG_COUNT`/`KEY`/`VALUE` in the command, replace refs, `i18n.logOutputEncoding`, a `-diff` attribute) and the conflict-resolution lines of a merge commit are not seen; a `cd` that only runs conditionally is followed as if it ran; a placeholder word on a line exempts that line from the secret patterns; denylist literals match as substrings; other `gh` operations that publish (`gh gist create --public`, `gh release create`) are not checked. Treat megavibe itself as expected-public: a line such as `github.com/poma-ai/megavibe` belongs in the known-public list. Tests: `/bin/bash tests/public-push.test.sh`.

**Trash review.** `rm` runs as `~/.megavibe/scripts/trash.sh`, which renames each item into `~/.Trash` as `<name> mv-<id>` and records it in `~/.megavibe/trash/ledger.jsonl`: original path, that exact Trash entry and its inode, size, session, working directory. Every later action first checks the entry is still the same object, so a name clash or a replaced entry can never redirect it. Finder's "Put Back" does not know these items; restore them through the review. Options it does not handle (`-i`, `-I`, `-x`), an item on another volume, or a rename the OS refuses go to `rmtrash` instead. An item on another volume lands in that volume's own Trash, `<volume>/.Trashes/<uid>`, and `trash.sh` then looks the entry up there by inode and records where it went (`trash_root`, `trash_path`) and its size, so the review treats it like a boot-disk item. On such a volume the inode, inside that checked Trash directory, is the identity (a remount can change a volume's device number). A volume that is not mounted is reported by `status` and skipped by every action; nothing is touched until it returns. The unreviewed totals include items still at their recorded Trash path with the recorded identity. Older records without a Trash location remain in the ledger for reference.

The `trash-watch.sh` hook (PostToolUse on Bash) stays silent until the unreviewed total reaches 1024 MB, or reaches 100 MB with at least one unreviewed item older than seven days. Set `MEGAVIBE_TRASH_REVIEW_MB`, `MEGAVIBE_TRASH_REVIEW_AGE_DAYS_MB` or `MEGAVIBE_TRASH_REVIEW_AGE_DAYS` to change those defaults (MB uses 1024 KB). `MEGAVIBE_TRASH_REVIEW_COUNT=0` opts into the former 30-item or 2048 MB thresholds. `MEGAVIBE_TRASH_REVIEW=0` silences the hook. The hook suppresses identified subagent calls. Explicit session attendance (`CLAUDE_CODE_SESSION_ATTENDED=1` or `0`) takes precedence over the hook payload, which takes precedence over the entrypoint. An empty or invalid payload requires explicit attendance to emit a notice. Permission mode alone says nothing about attendance. Remote Control bridge sessions skip entrypoint inference. Unattended runs stay quiet and leave the stamp alone. For attended runs, a machine-local stamp limits notices to one per due state, keyed by the total in whole MB and the newest unreviewed record ID. Then it tells the main session to dump the pending items, have a Haiku agent group them with a recommendation each, ask the user per group with AskUserQuestion, and apply the answers with `trash-review.py apply`:

| Action | Effect |
|---|---|
| Restore | moved back to its original path, never replacing anything there (an atomic no-replace rename) |
| Keep in Trash | marked reviewed, not raised by the hook again; a later group can still restore or back it up |
| Back up | moved to `MEGAVIBE_TRASH_BACKUP_DIR`, by default `megavibe-trash-backup/` in iCloud Drive (or in `~` without iCloud), under the date and the original path |
| Mark droppable | left in the Trash and reported by `status`, so the user can empty the Trash knowing what is in it; the review itself never deletes it; only the user, or the Trash greenlight script behind a permission prompt (below), empties it |

Nothing in the review deletes. Megavibe sessions run with permissions bypassed, and three review rounds found every agent-run consent check for a real delete forgeable (environment overrides, appends to the session transcript, a pseudo-terminal), so no consent check lives in the review: "droppable" items stay in the Trash, and `status` reports how many and how big they are so emptying the Trash is an informed choice. The emptying is a separate script behind a permission prompt the human answers (next paragraph), or Finder. Keep and Mark droppable leave an item reviewable: a later group can still restore or back it up (`pending --all` lists them). Every action first moves the recorded entry atomically into a private claim directory and checks its inode there, so nothing can swap it between the check and the action; checks that can fail (creating the parent, the backup directory) run before the claim, a failure after it puts the item back, and the next `apply` puts back anything an interrupted run left behind. A move to another volume copies (with `ditto`: resource forks, extended attributes, ACLs; a symlink as a symlink) to an exclusively created staging name, publishes with a no-replace rename, and leaves the original in the Trash: removing it would be a real delete. `status` also lists anything an interrupted review stranded in the claim directory. Groups are registered with `trash-review.py group`, which prints a summary line per group to quote in the question. `python3 ~/.megavibe/scripts/trash-review.py status` (counts) and `pending` (the items) work from any terminal. The ledger is best effort: without `python3`, or for an item whose entry cannot be found in its volume's Trash afterwards, the delete still goes to the Trash. `MEGAVIBE_TRASH_REVIEW=0` switches the hook off. Tests: `/bin/bash tests/trash.test.sh`.

**Trash greenlight.** `~/.megavibe/scripts/trash-empty.sh` deletes the items the review marked droppable; `trash-empty.sh --all` empties the whole Trash, including what the ledger never saw. It is the one place megavibe really deletes. What gates it is not a check the agent could run itself from a Bash command but Claude Code's own permission prompt. `setup.sh` (macOS) adds three `permissions.ask` rules to `~/.claude/settings.json` (and to `$CLAUDE_CONFIG_DIR/settings.json` when that is set), as a union with the ones you already have, never replacing a list: `Bash(~/.megavibe/scripts/trash-empty.sh *)`, the same path with `$HOME` expanded, and the catch-all `Bash(*trash-empty*)`. Per Claude Code's documentation an ask rule still prompts under `bypassPermissions` (the mode `megavibe` launches with), the `Monitor` tool follows the same Bash rules, and under Remote Control the prompt is forwarded to the phone: your Yes or No there is the decision. In a plain `claude` session in `dontAsk` mode the call is denied instead of prompting. Check it once on your machine: ask Claude to run the script while nothing is droppable; a prompt must appear in the terminal and on the phone, and No must leave `empty.log` unchanged.

What this guarantees, stated precisely: **the script runs only when Claude Code's own shell was given exactly the approved command, which Claude Code prompts for, unless the agent has rewritten Claude Code's own configuration (permission hooks, settings, plugins) or writes deleting code of its own.** It does not prove that a human answered the prompt. Those two cases are a documented boundary, not something this feature chases to the end; the cheap guards are below, and managed settings close the settings-file route for the ask rules but not for hooks (`allowManagedHooksOnly` would, and would also switch off megavibe's own hooks).

- **The script checks what Claude Code's shell was given.** Ask rules match the command text as written, so a spelling that reaches the file without the text matching (a glob, `cd` first, a variable, a symlinked directory, `env -C`) would skip the prompt, and a list of such spellings can never be complete. So the script does not trust the text it was started with. Claude Code runs a Bash call as a child of its own `claude` process, through a shell whose command line is `<shell> -c source <home>/.claude/shell-snapshots/snapshot-<shell>-<n>-<id>.sh 2>/dev/null || true && … && eval '<the command as typed>' < /dev/null && pwd -P >| /tmp/claude-<hex>-cwd` (measured on Claude Code 2.1.30x with zsh; a quote inside the command is rendered `'"'"'`). That command line is what the permission rules matched. The script walks its ancestors and runs only if (1) the topmost process called `claude` is a running process that satisfies Anthropic's Developer ID requirement (`codesign -v -R=…` against the live pid with team `Q6L2SF6YDW`, so a renamed look-alike, a copy or a tampered binary does not count), and (2) the shell directly below it has exactly that command-line shape with the payload `~/.megavibe/scripts/trash-empty.sh` or `~/.megavibe/scripts/trash-empty.sh --all`, matching the argument the script itself got, nothing else in the call. A bare `bash -c … && eval '…' < /dev/null` from a hook, an MCP server or a helper command does not have that shape. Anything else exits 5, including a plain terminal (even with a tty: an agent can start a Terminal window or a launchd job), a process started outside Claude Code (`osascript`, `launchctl`, `tmux`, a daemonised job), every spelling above, and a `claude` started inside another `claude`'s Bash call (run it from the outermost session). It relies on Claude Code's current way of running commands, on a native, signed install (an npm install shows up as `node`) and on `~/.claude` as the config directory (a custom `CLAUDE_CONFIG_DIR` keeps its shell snapshots elsewhere); if any of that changes, or a sandbox forbids reading the process table, it fails closed (exit 5) until the script is updated; Finder always works.
- **A PermissionRequest hook can answer the prompt for you, so two cheap guards.** Claude Code runs a `PermissionRequest` hook instead of asking you, and the hook can say Yes. The script therefore exits 6 while a non-empty `hooks.PermissionRequest` is visible in the managed settings file, `~/.claude/settings.json`, `~/.claude/settings.local.json`, or the `.claude/settings.json` and `.claude/settings.local.json` of the session's working directory and every directory above it (the working directories of Claude Code's shell and of `claude` itself, read with `lsof`; if neither can be read the script refuses with exit 5, because the project files cannot be checked). A settings file that does not parse is judged by its text and fails closed: any mention of `hooks` counts. The message tells the agent to ask you to remove the hook, not to remove it. `template/.claude/hooks/block-permission-hooks.sh` (a PreToolUse hook on Write, Edit and MultiEdit, run by `init.sh`) covers any `*settings*.json`, a plugin `hooks.json`, and the frontmatter of `.claude/agents`, `skills` and `commands` files: a Write that mentions `PermissionRequest` is refused; an Edit or MultiEdit is applied to the file as it is and refused if the result mentions it at least as often as before (adding one, splitting the word across two edits, and editing around a hook that is already there are refused; deleting one is allowed); a JSON `\u00` escape in a settings write is refused, and JSON that parses is checked with its escapes decoded. `block-dangerous-bash.sh` has a text rule for the Bash route (any command that mentions PermissionRequest next to a settings or hooks file, even to read it: use the Read or Grep tool). Both are text checks and a determined agent can write the same configuration another way (see "Not covered"). **A user with a harmless PermissionRequest hook of their own (one that only notifies) is locked out of this script while it exists**, and so would everyone be if megavibe shipped one, which it does not; to use the greenlight they remove that hook themselves, otherwise they empty the Trash in Finder.
- **The hook is only the first net.** `block-dangerous-bash.sh` lets exactly `~/.megavibe/scripts/trash-empty.sh [--all]`, alone in the call, through to the prompt and refuses other commands that name the script (`trash-empty`, `trash-em*`, `trash-e*`; quotes, backslashes, brackets, braces and newlines ignored, case ignored), a home-anchored path whose first part is a glob that can complete to `.megavibe` and that goes on below it (`~/.m*/scripts/x`, `~/.meg?vibe/x`; `ls -d ~/.m*` passes), and `osascript`, `launchctl`, `crontab` or `open -a Terminal` that mention `~/.megavibe` or the script (`launchctl list | grep com.megavibe` does not). Spellings that name nothing it can see (`cd -P ~/.megavibe/scripts && ./tr*h-e*`, `env -C …`, `$D/tr*h-e*`, `find … -exec {} \;`, a symlinked directory) pass it on purpose: the script refuses them (exit 5). The catch-all ask rule still prompts for any command whose text names the script, in projects without the hook too.
- **Over-blocks.** Any Bash text that names the script is refused, not only runs of it: `git add scripts/trash-empty.sh`, `bash -n scripts/trash-empty.sh`, `shellcheck`, `grep`, `cat` and a commit message that mentions it, and a path with a directory called `…trash-empty…` in it. Use the Read and Grep tools, `git add scripts/` (the directory), a loop over the directory for lint (`for f in scripts/*.sh; do bash -n "$f"; done`), `git commit -F file`. In your own sessions the catch-all rule also makes any such command ask first. Ordinary commands (`ls ~/.m2/*`, `cat ~/.mcp*.json`, `echo trash-export`, `ls ~/.megavibe/scripts/*.sh`) pass.
- **The environment is not trusted.** The shebang is `#!/bin/bash -p` (privileged mode: no `BASH_ENV`, no functions imported from the environment such as `export -f jq`), and the script refuses to run unless `-p` is in effect, so `bash trash-empty.sh` and `source` both exit 3. The path is fixed, the environment is wiped (`env -i`), python3 is looked up only in `/opt/homebrew/bin`, `/usr/local/bin` and `/usr/bin`, never through `PATH`, and the home directory is the user database's: a different `$HOME` is refused. `CLAUDE_CONFIG_DIR` is ignored: the rules must be, as a real array of strings under `permissions.ask`, in `<home>/.claude/settings.json` or in the managed settings file (`setup.sh` writes both locations when the variable is set, so the prompt exists wherever Claude Code reads it). That is the mechanism check, not consent: the consent is the prompt. Not a copy, a symlink or another install path (exit 3); rules missing or malformed (exit 4).
- **How it deletes.** One embedded python program (`python3 -I`), not a subcommand of `trash-review.py` (`python3 …/trash-review.py` is allowed and typable). It opens `~/.Trash` once with `O_NOFOLLOW` and works relative to that descriptor, so swapping `~/.Trash` for a symlink mid-run changes nothing. It reads the ledger as JSON (a newline or separator in a recorded path cannot become a record), accepts only a direct-child name (no `/`, `.`, `..`, trailing slash), and claims each entry with an atomic rename into a private quarantine directory inside the Trash, then checks it is the object the ledger recorded (device and inode) **after** the claim; if another object was swapped in, it is put back and nothing is deleted. The delete is directory-relative and never follows a symlink: a symlink in the Trash is unlinked, its target untouched. For droppable entries it adds owner write and search permission to directories and clears the user immutable flag where needed, using descriptors inside the Trash. It skips flag repair on files with other hard links. Two ledger records for one object that disagree (one kept, one droppable) skip it. A droppable item that is no longer in the Trash (restored, or emptied in Finder) gets an `emptied` row marked "already gone" and does not keep the run at exit 1. It holds the review's `apply.lock`, so it never runs in the middle of a review. An entry it cannot fully delete gets its name back, so a later run finishes it. The delete is plain `unlink`/`rmdir` on purpose: the `rm-to-trash.sh` hook rewrites the command text Claude runs, never the inside of a script. It raises its open-file limit so a deep tree can be walked, and if macOS refuses it access to `~/.Trash` it prints the system error with a Full Disk Access hint. There is no `--yes`, `--dry-run` or environment switch. Exit 1 means something was skipped or failed.
- **What a Yes consents to.** Yes means: delete what the Trash review marked droppable (for `--all`: everything in the Trash). The marks come from the review, where you answer per group, but `trash-review.py group` and `apply` can also be typed by an agent, so **a mark is not consent by itself and the prompt shows only the command**. If you did not just answer a review, look first: `python3 ~/.megavibe/scripts/trash-review.py droppable`. `--all` is for when you asked for it; the review procedure (`trash-watch.sh`) offers only the plain form, never retries a denied prompt, and a denied prompt is the answer. The installed script is a file your account can edit, so an edited copy would run after a Yes; the managed settings file protects the rules, not the script.
- **Interrupted runs.** TERM, HUP and INT end the python program cleanly (the entry it is on goes back under its name; the shell stub passes those signals on to the python child, which runs as its child so that the script's own shell stays in the process chain). KILL, or a power cut, can leave a claimed entry in a hidden `.megavibe-empty-<hex>` directory inside the Trash. The next droppable run, under the lock and before anything else, finishes the entries the ledger still marks droppable and puts every other back under its Trash name (or `recovered-<hex>-<slot>` when that name is taken or unknown), and says so; it never writes "already gone" for an object that is still there. Killing only the shell stub with KILL leaves the python child running to the end of the item it is on; it finishes and logs by itself. A `--all` run sweeps such leftovers like any other entry.
- **Record.** `~/.megavibe/trash/empty.log` gets one line per removed item (name and size) and one total line per run, including a run with nothing to do; every emptied item gets an `emptied` row in `reviewed.jsonl`, so it leaves `pending` and `status`. A droppable item on another volume is emptied from that volume's Trash: the script accepts only `<mount point>/.Trashes/<your uid>` (normalized, a real directory of yours on a mounted volume other than the home volume), pins it by descriptor, and claims and deletes exactly like a `~/.Trash` entry; an unmounted volume is reported (`not mounted`, exit 1) and nothing is deleted; `--all` still empties only `~/.Trash`. A droppable record with no device and inode (taken by the `rmtrash` fallback, or recorded before other volumes' Trash was tracked) cannot be emptied here: the run says so once, closes it with an `unemptiable` row so it does not fail every later run, and the item stays in the Trash for Finder. A ledger line that is not UTF-8 or a record that cannot be used is skipped, with a message, and the rest of the run goes on.
- **Stronger, opt-in.** `megavibe trash-greenlight` (or `bash ~/.megavibe/setup.sh --trash-greenlight-managed`) writes the same rules to `/Library/Application Support/ClaudeCode/managed-settings.json`, which an agent running as you cannot edit: it asks for your sudo password at a terminal, backs up an existing file once (to `managed-settings.json.megavibe-backup`, never overwritten, so the first backup is the original), refuses one that is not valid JSON, and unions with your other settings. Run `/status` in Claude Code to confirm it lists Managed settings. If your organisation delivers managed settings by MDM or remote policy, Claude Code reads that source and ignores this file.
- **Not covered.** (1) Deleting code the agent writes itself, as above. (2) Claude Code's own configuration, rewritten by the agent in ways the two guards above do not see: hooks in plugins or in agent and skill frontmatter, a hook or MCP server whose command line is written to imitate the shell's shape, and a second `claude` started detached with other settings (`--setting-sources`, another `CLAUDE_CONFIG_DIR`, `-p`) whose own shell is then given the approved text without your ask rules; anything that can answer or avoid the prompt without a human is outside what the script can see. (3) The rule-presence check reads a file your account can edit: an agent that removes the rules, runs the plain form (no prompt, because the rules are gone), and restores them from a background process timed to the script's check could pass it; the managed settings file closes that. (4) The script proves the call was the approved text, not that the prompt was shown, which is why the rules must be installed. (5) The launcher syncs the script, but only `setup.sh` adds the rules, so until it has run the script refuses (exit 4). (6) Whether `~` in a rule is matched literally is not documented, which is why the expanded path and the catch-all are installed too.

Tests: `/bin/bash tests/trash.test.sh` (sections 7-11: the hook's first net, the script in a scratch `HOME` with a rewritten copy for its test points, the settings merge, the provenance decision on fixture process chains, the PermissionRequest checks).

>
> **Gemini without Codex is rationed.** Outside a review the script refuses while Codex is usable, and otherwise runs flash-lite only (never Pro), with output capped at 12000 tokens, input at 300 KB, and at most 40 calls and an estimated $1.00 per local day; over any cap it exits 5 and the caller falls through to the Claude subagent. Every call is logged in `~/.megavibe/gemini-usage.jsonl` (`gemini-review.sh --budget` shows today's). Each call is reserved in the ledger under a lock before it is sent, an unreadable ledger refuses, the context watcher may use at most 60% of the day, and an unreadable cap value counts as 0. Tune with `MEGAVIBE_GEMINI_DAILY_CALLS`, `MEGAVIBE_GEMINI_DAILY_USD` (0 switches general use off), `MEGAVIBE_GEMINI_DIGEST_MODEL` (must be a flash-lite), `MEGAVIBE_GEMINI_MAX_INPUT_KB`, `MEGAVIBE_GEMINI_MAX_OUT`, `MEGAVIBE_GEMINI_PRICES`. The dollar figure is an estimate priced on the high side; your key's own project budget is the real ceiling. Reviews are never refused by the caps, only logged.
>
> **Antigravity CLI (Google's successor) is deliberately not the backend:** it works headlessly on a Workspace login, but it is an agent harness — ~13K tokens of system prompt per call, 2–4 minutes and 3–5x the tokens for the same review the API answers in 7 s, a weekly per-account compute quota with lockouts, and Workspace access is a Gemini Enterprise add-on. Measured 2026-09-06; revisit if Google ships a harness-free headless mode.

**Choosing which reviewers run.** Intermediate rounds get one independent reader; ship rounds normally get two that actually review the final candidate in full. Allocate each reader by continuous weighing: Codex + the Claude `reviewer` subagent or two different Codex models, plus available Gemini when pinned as a peer. Eligibility, the single-subagent floor, failures and backstop exceptions are defined in [delegation.md — Two review tiers](template/.claude/rules/delegation.md#two-review-tiers-and-why); critical work follows the same tiers. To configure backend eligibility:

```bash
megavibe reviewers                          # what is on, where it was set, what is available
megavibe reviewers set all                  # all backends eligible; add Gemini to allocated ship readers
megavibe reviewers set reviewer codex       # never Gemini, not even as a fallback
megavibe reviewers set --project reviewer   # this project only (uncommitted)
megavibe reviewers set auto                 # back to the default
```

**Why Gemini is the fallback reviewer.** Measured across one day of paired reviews (11 units where both read the same diff with the same prompt): Codex — which reads the repo, runs the tests, and reproduces the failing input — found real defects in every unit. Gemini, a single stateless API call over inlined files, produced four wrong headline findings and five SHIP verdicts on code with confirmed blockers. It also produced one unique real catch that nothing else found — an argument for `set all`, not for the default: under the default it does not review at all on a day when Codex works, so that class of catch goes to zero. It stays in the chain because it is the only EXTERNAL review capability on a machine without Codex, where it takes Codex's place in the default set alongside the subagent, and because it covers the days Codex is out of quota. To keep the third opinion at roughly $0.15 a review, run `megavibe reviewers set all` and treat its findings as leads to reproduce rather than as verdicts.

The Claude `reviewer` subagent can never be made ineligible — it needs no key and provides the fallback floor — but eligibility does not require it to run alongside two successful Codex readers. The setting controls external backend eligibility; [delegation.md](template/.claude/rules/delegation.md#two-review-tiers-and-why) governs the readers allocated to each round. It writes `MEGAVIBE_REVIEWERS` into the `env` block of `~/.claude/settings.json`, or — with `--project` — the project's uncommitted `.claude/settings.local.json`; the environment variable overrides both. A **committed** project `.claude/settings.json` is read too, but it may only *add* reviewers: a file that arrives with a clone must not be able to switch off the reviewers looking at that clone's code. The session-start status table gains a Reviewers row, and a reviewer you switched off exits without spending anything when asked to review.

It limits **reviews only**. Gemini and Codex stay available for context recovery, summaries and large-context work whatever you set here — switching a reviewer off should not cost you `/rehydrate`.

### Parallel tasks (spinouts)

When a plan has 3+ independent tasks, Claude can spin them to parallel subagents. Each gets a fresh context window. The primary benefit is **context freshness**, not just speed.

A job over many bulky items (images, PDFs, long logs) is split the same way by context size: on one measured image-labelling job, one long subagent cost an estimated 2-4x more than batches kept under about 250K tokens would have (it pays only while each batch's fixed briefing stays small). Rule and numbers: `.claude/rules/spinouts.md`, "Batch jobs".

A subagent's prompt cache lives 5 minutes by default (the main thread's usually 1 hour), so a foreground wait past that re-writes its whole context. Spin-out briefs therefore carry a wait limit of 170 s per call and a sentinel-file recipe for waiting on long jobs; waits over about 35 minutes belong to the parent. Measurement and recipe: `.claude/rules/spinouts.md`, "Subagents: keep the cache warm while waiting".

## Launch records

Every session the `megavibe` wrapper starts is recorded in `$MEGAVIBE_HOME/launches/<claude pid>.json` (default `~/.megavibe/launches/`; owner-only; dead processes are pruned at the next launch): `{pid, launcher: "megavibe", parentSessionId, parentPid, parentCwd, startedAt}` (`parentPid` is the live parent's pid when the registry knows it: a session's id changes on `/clear`, its pid does not; `parentCwd` is the parent's directory, used to tell a resumed parent from one that ended). Claude Code's own session registry (`~/.claude/sessions`) has no parent field, so tools that list sessions join this record by pid. `parentSessionId` is `MEGAVIBE_PARENT_SESSION` when set (empty means no parent; the wrapper reads it once and removes it from claude's environment, so it applies to that launch only; `megavibe node ...` and `megavibe assistant` pass an explicit value on to the window they open, and a restart of the wrapper itself keeps the parent it resolved at first launch, even after the parent ran `/clear`), else the launching session's `CLAUDE_CODE_SESSION_ID`, believed only while an ancestor of the wrapper is that session's registered process (`~/.claude/sessions/<pid>.json` names that id; no process-name matching), else null (a session you started yourself). A launch from a session's Bash tool is linked automatically. A launch that is not that session's child but runs on this machine (tmux, a LaunchAgent) must pass `MEGAVIBE_PARENT_SESSION=$CLAUDE_CODE_SESSION_ID` (same machine only: a parent on another host is not in the local registry): a tmux server hands every later window the environment of whoever started it, so an inherited id can name an unrelated session, and the ancestor check ignores it. Recording never blocks or fails a launch. Test: `tests/launch-record.test.sh`.

`megavibe sessions` lists the live Claude sessions on the machine (name, pid, state, age, whether megavibe started it, directory) as a tree, children under the session that launched them. `megavibe sessions --orphans` lists only the orphans: live sessions whose launcher session has ended, which a tmux-launched helper nobody remembers becomes (its parent is the tmux server, so it never shows up as PPID 1). The session-start table gets an "Orphaned sessions" row when there are any, and is silent otherwise. A parent found by neither pid nor session id (`/clear`, then resumed under a new pid) is listed as "not found" instead of "ended" when a newer live session that is not a sibling runs in the parent's recorded cwd, but the hook line counts both alike (an alarm a new session in the directory could silence would stay quiet where the user mostly works). A helper meant to outlive its session is launched with `MEGAVIBE_PARENT_SESSION=` (empty). A registry file whose `procStart` differs from the live process's start time (a stale file on a reused pid) is skipped. Only sessions the wrapper launched with a parent are linked: a session you started yourself has none, and `claude -p` workers leave no record. Names and paths are reduced to a safe character set before printing. Test: `tests/sessions.test.sh`.

## One writer per conversation

Claude Code lets an ordinary session be resumed while another process still has it open; both then append to one transcript, and messages from one of them can be missing when it is resumed later ([sessions](https://code.claude.com/docs/en/sessions.md), "Branch a session"). So `megavibe --resume <id|transcript path>` (also `-r`, `--resume=`) is refused, exit 3, only when a record in Claude Code's session registry (`~/.claude/sessions/<pid>.json`, or under `$CLAUDE_CONFIG_DIR`) has that session id, its pid is alive, and its recognised start time matches that pid's; missing, unparseable or mismatching start times and unresolved names pass silently (the live-process registry cannot establish a unique saved conversation by name in this project). The message gives the pid, the tmux pane with a read-only `capture-pane` command and how to attach, `--fork-session` to keep both conversations, a fresh session, and `--allow-second-writer` for a user who means it. The other process is never signalled, stopped or typed into. The check runs first, before the launch root, project initialisation and the login check, so a refused resume does not initialise the project it was run in (the update check and the personal assistant's hook sync still run before it). **Unmeasured on Linux:** the start-time comparison is exact text, measured against the registry on macOS only (`ps -o lstart=` in UTC); what Claude Code records on Linux has not been established, and if the two forms differ the check passes (no refusal) rather than guess a tolerance. Not checked: a bare `--resume` (the picker) and `--continue`, which Claude Code resolves itself; a `--fork-session` (new id); a running background session, which Claude Code attaches to rather than opening twice; and anything the wrapper cannot establish (no `jq`, an unreadable record, `ps` failing), which passes rather than blocking a legitimate resume.

## Shared memory routing (optional)

You do not need any of this. The baseline is `.agent/`: `DECISIONS.md`, `LESSONS.md` and `RESEARCH/` are tracked in git, so teammates get them with the repo, and the Grep and Glob hook searches them through local poma-memory. Shared memory and a document server are opt-in additions for sharing across repos and for long documents. With neither configured, the only cost is a short rule (about 440-480 tokens including one line in the protocol) and one Bash call that prints nothing, only when some MCP exposes a `memory_search` tool, when an MCP tool named `*ingest*` is visible and (a document question comes up or you hand Claude a substantial document), or when you ask about Megavibe's shared memory or document server or ask it to store a document there (a general question about document storage in your own code does not count); the long text (`~/.megavibe/template/.claude/shared-memory-full.md`; the rule never reads the gitignored copy `init.sh` still installs into a project) is read only when a `MEGAVIBE_MEMORY_*` value is printed or you ask why it is not working.

`.claude/rules/shared-memory.md` is a stub that loads `~/.megavibe/template/.claude/shared-memory-full.md`, which has two independent parts. With a shared-memory MCP connected (tools `memory_search` and `memory_ingest`), it routes each search to one scope (this repo, general knowledge, or organisation-wide guidelines) and sends short records there while long documents go to a document-indexing MCP. The repo scope is labelled by `scripts/repo-id.sh`, the normalized `org/name` of the `upstream` or `origin` remote. `MEGAVIBE_MEMORY_SERVER` names the MCP server that gets used (the `<server>` part of its tool names, `mcp__<server>__memory_search`, compared exactly); unset, the feature is off, so a third-party server that happens to expose the same tool names never receives your entries. The general and organisation scopes are `org/name` labels your server's operator names; set them in the `env` block of `~/.claude/settings.json` as `MEGAVIBE_MEMORY_GENERAL` and `MEGAVIBE_MEMORY_COMPANY`. An unset variable disables that scope. A backend whose tools lack the `repos`/`kind` (search) or `repo`/`kind` (ingest) parameters still works: the parameter it cannot take is dropped, so searches run unfiltered and records are written without that label. `MEGAVIBE_MEMORY_DOCS` names the document MCP server; unset, documents are not stored and document questions go to web search as before. When it is set, questions about an ingested document search it before the web (an empty result or an error makes Claude ask before any web search, unless the question is plainly about public material), next to a scoped memory search, and Claude says in one line what the first document search of a session sends (question text, file name filter) and what each duplicate check sends (title, file name), asks first when the question names something that looks private, and asks once whether a substantial new document you hand it should be remembered there (never ingesting without a yes). Every ingest carries the file name as the `filename` attribute, and Claude checks whether a handed document is already stored before asking. Set `MEGAVIBE_MEMORY_DOCS_ASK` to any non-empty value other than `1` (`megavibe memory set docs_ask 0`; an unquoted `0` or `1` in the settings file is not a string, so it counts as off too) to stop the offers; an empty value is unset, so offers continue (explicit store requests always work). Writes to the general and company scopes happen only when you ask for them. Claude says in one line, before the first scoped search of a session and before each short-record write, what is sent and that every user of the server can read it (for repo scope, including the repo's `org/name`). Without the MCP, or with a backend that does not support labels, nothing changes.

Set every `MEGAVIBE_MEMORY_*` variable in the `env` block of your user-level `~/.claude/settings.json`, and only there. `megavibe memory` shows what a session will trust, and `megavibe memory set server <name>` (also `docs`, `docs_ask`, `general`, `company`) and `megavibe memory unset <key>` write the quoted-string values for you. A cloned repo can commit a `.claude/settings.json` or `settings.local.json` whose `env` block Claude Code applies over yours, so a value found in the shell or a project file is never honoured. `scripts/memory-config.sh` reads only your user-level file (found through `$HOME`, with `PATH` pinned to `/usr/bin:/bin:/opt/homebrew/bin:/usr/local/bin`, so a `jq` elsewhere gives `UNAVAILABLE`) and prints `KEY=value` for plain tokens (letters, digits and `._:/@-`). It prints `INVALID <name>` for anything else, `IGNORED <name>` for a variable present only in the shell or a project file (name only, never the value), and `UNAVAILABLE (reason)` when it cannot run. An empty or null value means unset; any other non-string value (an unquoted `0` or `true`) prints `INVALID`, so write values as quoted strings. When `CLAUDE_CONFIG_DIR` is set the script prints a fixed `NOTE` line, because it reads only the default location; managed (organisation) settings are not read either, so put these variables in the default user file. Claude mentions `IGNORED`, `INVALID`, `NOTE` or `UNAVAILABLE` only when the script also printed a configured value or you bring up shared memory yourself, so a user who configured nothing never hears about it; the cost is that anyone whose values are all outside `~/.claude/settings.json` (only in the shell or a project file, or under `CLAUDE_CONFIG_DIR`), or whose script prints `UNAVAILABLE` (`jq` outside the pinned `PATH`, an unreadable settings file), is silently off until they ask why it is not working, which makes Claude run the script and say what it found. Limits, stated plainly: a repo whose settings can set `HOME`, `PATH`, `BASH_ENV` or exported `BASH_FUNC_*` functions, or whose hooks you accept, already controls every command in the session and this check does not defend against that (the script pins `PATH` and drops the functions it names, as a best effort); a project `.mcp.json` can register a server under the name you configured; a repo can commit its own `.claude/rules/` files; and the repo label comes from the repo's own git remote, so a repo can claim another organisation's `org/name` scope. The server name is compared exactly against the `<server>` segment of the tool names; if Claude Code rewrites characters such as `.` in a server's name to `_` there, set the variable to the rewritten form you see in the tool names. `repo-id.sh` keeps only `org/name` and ignores the host, so the same `org/name` on two forges shares one repo scope; GitLab subgroups, Azure DevOps, organisations containing `_` or `.`, and one-letter scp hosts (`x:org/name`, read as a Windows drive) give no id, and the repo scope is then skipped.

The document server behind `MEGAVIBE_MEMORY_DOCS` can be any MCP server that meets these requirements:

- Ingest: a tool that takes a whole file or URL and does the parsing, chunking and embedding itself. A bare vector database that only stores text you chunk yourself does not qualify. The tool's name must contain `ingest`: that is the only signal that makes Claude check the setting on a document question. An explicit request to store a document in the document server or shared memory is a trigger of its own, so a configured but disconnected document server (no tool visible) still gets the "not stored" answer.
- Search: a tool that returns passages together with their source document. Restricting a search to one document is optional.
- Document list (optional): without it, the duplicate check is skipped and Claude asks the usual question.
- Attributes and filters (optional): used to record the file name as a `filename` attribute and to look it up. Where the ingest tool has no `attributes` parameter, Claude omits it.

## Subscription-first routing

Megavibe prefers the subscriptions you already pay for over anything billed per token, and uses what they report about themselves to spend them sensibly.

- **API billing is barred.** A launch that would bill per token (`claude auth status` reporting `api_key` or `api_key_helper`; a subscription OAuth token is fine; a Bedrock/Vertex/Foundry or other third-party provider only gets a notice, since that is a cloud bill, not a Claude one) stops with one line on the main `megavibe` launch; `MEGAVIBE_ALLOW_API_BILLING=1` accepts it. An exported `ANTHROPIC_API_KEY` is masked for that session, as before. `megavibe assistant` starts the PA's session through this wrapper too, so it is covered; keys passed through `--settings` are not, nor the one-line workspace-trust preflight `pa-start.sh` runs with `claude -p` the first time a folder is not yet trusted.
- **Usage history.** Claude Code has no usage API, but the statusline receives your account-wide five-hour and seven-day usage (`rate_limits`, subscribers only, after the first reply). `statusline.sh` appends a row to `~/.megavibe/usage/claude.jsonl` on a change or every five minutes. Nothing leaves the machine and nothing reads credentials.
- **Launch.** `scripts/usage-route.sh` classifies the account as `over` (7-day use at 90% or projected past 100% of the week; in the first quarter of the week, before there is a projection, 30 points ahead of a straight-line pace, held until the projection takes over; or 5-hour use at 85%), `under` (week on pace to use less than 70%, or capacity about to reset unspent) or `normal`. `over` launches with `--model sonnet --effort medium` where your defaults are higher; `under` launches with `${MEGAVIBE_ROUTER_UP:-opus}` where your default is lower, but an upgrade to Opus (or Fable) only on a Max plan (`claude auth status` reports `subscriptionType`; a lower `MEGAVIBE_ROUTER_UP` target is not plan-gated): a lower or unknown plan keeps the model it chose, Sonnet unless it picked otherwise, because Opus spends a Pro limit several times faster. Hysteresis releases `over` 30 minutes after its leave thresholds first hold (the highest reading of a window is remembered, so a reading of 85% or more holds `over` until the window resets or the projection falls with elapsed time; delete `~/.megavibe/usage/route-state.json` or set `MEGAVIBE_ROUTER=0` to override), and requires two qualifying evaluations 30 minutes apart for `under`; `under` lasts only while its qualifying reading holds (the five-hour window that justified it resetting ends it), and with no live window both bands are `normal`. Which window is live is decided by its reset time, not by the order rows were logged. Concurrent sessions are merged by taking the highest reading of the current window, which the router also remembers in `route-state.json` so a flood of late, lower rows cannot hide it. No data or a reset window is `normal`, which changes nothing; a reading older than 6 hours inside a live window still counts toward `over` (usage only grows inside a window) but never toward `under`. `under` upgrades from the model in `~/.claude/settings.json`, so it needs one there. The history keeps its newest 5000 rows past 2 MB and does not tell accounts apart (one account per `~/.megavibe`).
- **Your choice wins, per half.** `--model`/`--effort`/`--settings` on the command line, a resumed conversation (`--continue`, `--resume`, `--from-pr`) and `MEGAVIBE_ROUTER=0` switch the router off. A model set by `ANTHROPIC_MODEL`/`ANTHROPIC_DEFAULT_MODEL` or a project `model` is left alone, and so is an effort set by `CLAUDE_CODE_EFFORT_LEVEL` or a project `effortLevel`; the other half can still be routed. `megavibe route` prints what a launch would do.
- **Mid-session.** `usage-advisory.sh` tells the session when the band changes, and again after `/clear` or a compaction, how to spend subagents (pin `haiku`/`sonnet` when hot; let judgment-heavy ones inherit when capacity would be lost), and says when usage is back to normal. It also relays the balance advice below, and withdraws it when it stops applying. Its messages also carry both subscriptions' projections: the one the band and balance use (linear, else used percent) with the recent-rate projection beside it. It also speaks once at each session start, `/clear` or compaction when a projection is known, and on a later projection move it repeats only that line.

- **Codex, same engine.** `usage-route.sh codex` runs the same bands on the weekly figure Codex records in `~/.codex/sessions/**/rollout-*.jsonl` (ChatGPT login only; only this machine's calls appear, so a Codex also used elsewhere under-reads, and a reading counts as stale after 24 hours). The Codex band is advice (`megavibe route`, and `usage-route.sh balance` below); it changes no review. Until 2026-10-11 the `under` band raised an unspecified review to `xhigh`. That was removed: a blind benchmark found `xhigh` no better than `high` at about twice the time, and in real use both reviews of large PRs it raised timed out at 900 s, where the config's own effort answered in about 8 minutes. `over` changes nothing either: the review floor does not drop, and a Codex that runs dry already falls to the `reviewer` subagent.
- **Balance.** `usage-route.sh balance` compares the two weekly projections. When one subscription is running hot and the other is not, or they differ by 20 points or more, the advisory hook tells the session which one optional work (digests, exploration, second opinions) should lean on. It is advice for the model's own routing, not a gate: `reviewers.sh digest-chain` is unchanged. `megavibe route` prints both bands and the balance. For allocation at every unit of work, follow the [continuous allocation rule in delegation.md](template/.claude/rules/delegation.md#universal-fallback-principle), including implementation and fix rounds. These threshold bands are subordinate router advice, not allocation triggers or a fixed provider split. Each side counts at its effective projection: the router projection, else the straight-line estimate (used over the elapsed fraction, from 5 percent of the window, shown as `[linear estimate ~N%]`), else the used percent, so a subscription early in its window on a high straight line is never recommended.

- **Recent-pace forecast.** `usage-route.sh forecast` (and `megavibe usage forecast`, both providers) prints `provider|used|fc_pace_per_h|forecast|spare|spend_per_h|basis` for the selected weekly window. Pace is a property of time, not of the window: it is the use over the trailing 6, 24 and 168 hours, summed across resets, so it exists from the first minute of a window. Per weekly window the use is the highest reading up to now minus the highest reading before the horizon began (a window that began inside the horizon counts from 0, so after a reset the new reading is the use since it); row-to-row changes are never summed, because several sessions write readings that lag by a point, which inflates such a sum several times over. The forecast pace is 0.6 x the 6-hour plus 0.4 x the 24-hour pace (basis `6h+24h`; `6h` or `24h` when only one exists), else the 7-day pace (`7d`), else the window average (`week`, one reading only). An eighth field, `forecast_7d`, is the forecast at the 7-day pace. Forecast is `used + pace x hours_left`, spare is the target (95, `MEGAVIBE_USAGE_TARGET`) minus the forecast, and `spend_per_h` is the points per hour that would land exactly on the target. Unknown only with no history, no window or a stale newest reading. The pace crosses resets, so a busy day gives the first reading of the next week a high forecast (1 point per hour over 168 hours is 168%); that is intended: the forecast describes where the current pace leads, and it is weaker evidence early in a window (readings are whole percents, so the 6-hour pace is uncertain by about a sixth of a point per hour, and a pace built from a span of only one or two hours moves the forecast by tens of points per percent; a pace needs a span of at least an hour, so the forecast steps at that mark). Both percentages are account-wide server figures (other apps included), so the forecast models the total, never a per-session share. `balance` and its leaning rule, the `usage router:` projections line of the advisory hook and the `usage:` line of `tick.sh` lead with the forecast (the straight-line and recent estimates stay beside it). The `status` and `pace` lines are byte-identical to before, and the bands (`over`, `under`, `normal`) still decide on the straight-line projection: their hysteresis and the `under` guard were tuned on it, and a pace-based `over` would flap on one busy afternoon. `amass.sh`'s split keeps weighting by `pace` (recent, else linear). Tests: `tests/usage-forecast.test.sh`.
- **Which windows Claude Code reports.** The statusline records the key names (never values) of the `rate_limits` it receives in `~/.megavibe/usage/claude-shape.json`; `usage-route.sh windows` reads it. Measured 2026-11-24 on Claude Code 2.1.331, Max plan: only `seven_day` arrives (the docs list `five_hour` for Pro, Max and Ultra, but it is absent here), so every history row carries `fh:{p:null,r:null}` and the router's 5-hour condition has nothing to see; no five-hour forecast exists until Claude Code sends it. The statusline reads `five_hour.{used_percentage,resets_at}` as documented and fills `fh` the moment it appears (`tests/statusline-usage.test.sh` covers both payloads). Other sources exist (an OAuth usage endpoint) but need a token and the network, which a statusline hook must not use.
- **End-of-window sprint.** `usage-route.sh sprint` (and `megavibe usage sprint`, both providers plus the advice rendered from those same rows by `usage-route.sh sprint-render`) prints `provider|state|hours_left|used|forecast|spare|spend_per_h|basis|reason|five_hour_projected` (the last field is the five-hour used percent plus its recent climb, empty on `off` and `outside` rows where it is not computed, the highest pair rate over the last hour continued through the age of that reading plus a 30-minute unit). State is `sprint` when the weekly window has at most 4 hours left (`MEGAVIBE_SPRINT_HOURS`, 1 to 24), the recent-pace forecast and the used percent are both at least two points below the sprint target (99, `MEGAVIBE_SPRINT_TARGET`, a whole number below 100; the margin covers whole-percent readings and other sessions on the account), the newest reading is at most 35 minutes old (inside the window the Codex reading is re-read past its two-minute cache) and the five-hour window, where there is one, is below 85% (its climb, the highest rate over every pair of a recent reading (the last hour) and an earlier one (within 30 minutes, or the row just before it up to two hours back), a rise of two points or more rated one point higher because the readings are whole percents, continued through the age of that reading plus a 30-minute unit, is counted); otherwise `-` with the reason (`outside`, `no-forecast`, `5h-hot`, `no-room`, `off`). In sprint mode the steepest rise of 2 points or more over every pair of a recent reading (the last 90 minutes) and an earlier one (within 90 minutes of it, or the row just before it whatever its age), rated (rise + 1) over the time from the earlier reading to now (floored at 30 minutes, so a steady climb is not read as a burst) because the readings are whole percents (a single one-point tick is noise, an earlier dip does not switch it off), raises the pace to that rate (basis gets `+burst`), and the forecast is projected from the newest reading to the reset, not from now (rows are ordered by position, so two readings in the same second keep their order; an empty cached Codex read is re-read once, past the cache, so readings written since are seen), because the blended paces need a span of at least an hour over their horizon and miss a burst that has just started; under 10 minutes left is `outside`. `spare` is the sprint target minus the forecast and `spend_per_h` the points per hour, for the whole account, that would reach it; both are estimates. `usage-route.sh sprint-advice` turns that into one sentence per sprinting subscription, which `usage-advisory.sh` relays when the state starts, at each session start, `/clear` or compaction while it lasts, and withdraws when it ends: put that subscription's top model tier on the hardest open work for as long as `megavibe usage sprint` reports `sprint` for that subscription (it ends when the forecast or the used percent comes within two points of the sprint target, at the reset, or on a reading older than 35 minutes); the 95% target is replaced for that subscription and window only, the 100% backstop and the review floor are not. It is advice and nothing else: bands, the launch model, `balance`, `forecast`, `status` and `pace` are unchanged, and a session that never meets the state sees no difference (`MEGAVIBE_SPRINT=0` switches the advice off). Known limits: a burst that has not yet produced a two-point rise is invisible (measured: under 2% of sprint states overshoot, all in bursts under 30 minutes old); for a provider sampled only every 30 minutes (Codex, kept fresh by the PA probe) a burst younger than about 60 minutes can carry the advice to the cap, so the effect is hitting the limit shortly before the reset (the 100% backstop is unchanged); the sprint can flap near its two-point margin; a Codex history whose uncached scan takes over 2 seconds reports unknown for Codex and the hook keeps the state it last told. Rule text: `delegation.md`, "End-of-window sprint". Tests: `tests/usage-sprint.test.sh`, `tests/usage-advisory.test.sh`.
- **Codex usage probe (on for PA Macs, absent otherwise).** Codex writes a usage reading only when it is called, so between jobs its reading ages and the forecast goes stale. On a Mac where the Personal Assistant is switched on (`pa.on`, see README-node.md) the node's five-minute run calls `usage-probe.sh run --every 30`: one minimal `codex exec` at most every 30 minutes (cheapest model `gpt-6-luna`, `MEGAVIBE_PROBE_MODEL` to change; read-only, scratch directory; about 15K mostly cached input tokens, 5 output tokens), skipped when a Codex reading under 15 minutes old exists or codex is missing, never two at once, logged to `usage/probe.log` in the megavibe home. `megavibe usage probe status` says whether it is on; `run` does one probe by hand. Plain megavibe use with no PA never makes the call, and nothing installs a scheduler or runs `launchctl`. A Mac whose node was installed before this change gets the call after `megavibe node install` refreshes its `node.sh`.

`scripts/usage-route.sh pace` reports `provider|used|elapsed_pct|linear_proj|recent_pts_per_day|recent_proj|remaining_days` for `MEGAVIBE_ROUTER_PROVIDER` (`claude` by default, or `codex`). Linear estimates start at 5% elapsed. Pace uses the same weekly window and usage as `status`; balance and tick obtain status and pace from one history snapshot per provider. Recent estimates use only observations within three minutes of that selected reset epoch, sorted by timestamp, so delayed or interleaved readings cannot supply another window's trend. The rate between the earliest and latest distinct samples within six hours is projected from the last observation: `used_at_last + points_per_day * (reset - last.t) / 86400`. Elapsed percentage, linear estimates and remaining days retain the router's current-time base (`remaining_days = (reset - now) / 86400`); an expired window supplies no pace values. Fewer than two samples, any percentage drop in the retained window, or a last observation that disagrees with the router's selected usage leaves recent fields empty. Missing/stale readings leave all pace numeric fields empty (Claude: 6h, Codex: 24h). Balance and tick show both subscriptions' estimates beside lean advice, tagging early projections `[linear estimate ~N%]` and showing recent estimates with their burn rate, e.g. `(recent estimate ~109% at 4 pts/day)`. A recent estimate requires a non-negative rate; zero is valid. If status serialization fails or is empty, the display reports no data and balance gives no advice. If only pace serialization fails, valid status remains available without pace estimates. These estimates never stop work; routing bands and thresholds are unchanged.

A running session's model cannot be changed from outside, so the launch is the only place the router acts on the main thread. Spare Anthropic capacity at reset is lost, so is spare Codex capacity; the point of the balance is that neither runs dry while the other idles.

### Unattended windows: ticks, login lifetime, quota

A session left running while you are away (a long autonomous job, a phone-driven Remote Control session, an overnight queue) has two ways to go quiet without anyone noticing: nothing wakes it when a colleague asks for a review, and the login can lapse under it. Three pieces cover that; all of them are deterministic scripts the model acts on, not model calls.

- **`/watch [interval] [org/repo ...]`** schedules `~/.megavibe/scripts/tick.sh` as a recurring prompt in the session (default every 30 minutes, clamped to 10–50; the Claude Code cron lives in the session and expires after 7 days; `/watch status`, `/watch off`). One tick reports, since the previous tick, what happened on the watched repos (PRs updated, with their author; reviews and issue and review comments from other people; review requests addressed to you are listed on every tick while they are open), Linear comments when switched on, the login lifetime and both subscriptions' usage, with a first line of `NEEDS ACTION (n)` or `quiet`. The session answers what needs an answer and says one line. Configuration is personal and never in a repo: `~/.megavibe/personal/tick.conf` with `TICK_REPOS`, `TICK_PEOPLE` (logins whose activity is marked `!`), `TICK_LINEAR=1`, and `TICK_AUTH_HOURS`; the script header lists the rest. Linear uses `LINEAR_API_KEY` first, then the stdout of `TICK_LINEAR_KEY_CMD`, then `TICK_LINEAR_KEY_FILE` if no command is set. Set `TICK_LINEAR_KEY_CMD` only in personal `tick.conf`; inherited values are ignored. `TICK_LINEAR_KEY_CMD_TIMEOUT` sets the timeout in positive integer seconds (default 10). A command that fails, returns an empty key, or times out leaves the tick incomplete and keeps the window. `megavibe tick` runs one from a terminal. The window is exact and half-open (`~/.megavibe/tick/<name>.last`; an item stamped at the mark belongs to the tick that made it), your own PRs, comments and reviews and every `[bot]` account are left out, lists are paged (up to 2,000 PRs or comments per repo and window; reviews on up to 30 updated PRs per tick, the rest listed as unchecked for a look by hand; 60 report lines per repo, the full report in `<name>.report`), and a `gh` or Linear call that fails or runs past a limit, a misconfiguration (no `gh`, Linear on without a key) or a state file that cannot be written is reported in place, not retried, the first line says `INCOMPLETE` and the window is kept (its start in `<name>.pending`, written before polling), so the next tick covers the same span again rather than silently dropping what that call would have returned; `tick.sh --reset` abandons such a span on purpose. Quoted comment and title text in the report is third-party content; the skill's prompt says so and the session treats it as data. A tick inside the main thread's one-hour prompt-cache lifetime reads the cached context instead of rewriting it; that is a side benefit of work worth doing every half hour, not a reason to tick an idle session (`delegation.md`, "Cache heartbeat", leaves that question open).
- **`megavibe auth [HOURS]`** (`scripts/claude-auth-check.sh`) says how long the login lasts, without printing a secret or the account: the login's own expiry from `claude auth status`, and only when that is unavailable the access token (about 8 hours, renewed on its own) and the refresh token (weeks) from the macOS keychain entry Claude Code writes, else `~/.claude/.credentials.json`. A stored record can be stale (an expiry of 0 has been seen on a working login); an expiry it cannot use is reported as unknown, never as expired. The date parsing is tested with jq 1.7, not 1.6. The login lifetime is the one that matters: when it lapses the session dies with "Login expired", running subagents die with it, and `/login` is not available over Remote Control, so nobody can fix it from a phone. Exit 1 inside the horizon (default 12 hours) with the remedy: `/login` at the laptop, or `claude setup-token` for a long-lived headless token, before the unattended window. The session-start table carries the same line, and every tick repeats it. Measured once, 2026-10-31: a login that expired at 20:40 killed a fix agent mid-edit and left twenty scheduled ticks unprocessed until the next morning.
- **Quota in the tick.** The `usage:` line is `usage-route.sh status` for both subscriptions (used so far, the projection for the end of the weekly window, time to reset, a stale flag) plus the balance preference when there is one, so an unattended session sees the same numbers the launch router and the advisory hook use, every tick.

## Deliverables and open decisions

A session hands you work in one visible place instead of burying it in the hidden `.agent/` directory or leaving it on a hosted page.

- **`megavibe-deliverables/`** in each project root (created and gitignored by `init.sh`): reports, review syntheses and plans as clean Markdown or HTML, plus built artifacts handed to the user or a client in dated subfolders (confidential ones owner-only and not sent to the phone without your say-so). Nothing in it is committed; move a file out when it graduates.
- **`megavibe-deliverables/STATUS.md`** is the live file: what is going on, and every decision you owe as a numbered `D<n>` block with options, a default the session proceeds on, and an `Answer:` line. Type an answer into the file at any time; `status-sync.sh` (session start, every prompt you send, and every tool result while a session works) hands new answers to the session, which acts on them and moves the block to "Decided". The text is capped, is treated as a choice or short instruction (never as authorisation for a destructive action), and a `STATUS.md` that git tracks is ignored. `megavibe worktree remove` refuses to delete a worktree whose own `megavibe-deliverables/` holds anything beyond the two untouched template files.
- **`## Asked for`** in `STATUS.md` is the register of what you asked a session to write (ask, date, file, mirror, state). A request is `done` only when its file is in the folder: a chat answer or a note in `.agent/RESEARCH/` does not count. At each compaction `on-pre-compact.sh` hands the next model counts only (open asks, rows marked `done` whose file is missing, while something is open the number of `.agent/RESEARCH/` files from the last 14 days newer than everything in the folder except STATUS.md and README.md, a heuristic, and a `Now` section over about 4000 bytes): never text from the file, since a cloned repo can ship its own `STATUS.md`. Added after an audit found eight asks in one project that never became a file.
- The protocol bans open ends inline ("your call", "later", "say go"): an owed decision goes into STATUS.md, and the session continues on its stated default or says it is blocked on that D-number. Format: `.claude/rules/deliverables.md`.

### Per-project (automatic on first `megavibe` run)

Not in your home directory: there `.claude/` is your user-level config, so hooks installed into it would fire in every project, and a session there would run with bypassed permissions but no guard hooks. `megavibe` refuses to start in `~` (cd into a project, or run plain `claude`), and `init.sh ~` installs nothing. In a folder that is not a repo but holds several (an umbrella like `~/dev`), the launcher names the repos whose own `.agent/` log is newest: there, memory and `.agent/` are one bucket for all of them and, by default, no repo's own decisions, lessons or tasks are read (`MEGAVIBE_EXTRA_AGENT_DIRS` adds other repos' `.agent/` to search only), so launch inside the repo you change and reach a second one with `--add-dir`. If an older launch from `~` already installed hooks, `setup.sh` says which registrations in `~/.claude/settings.json` to delete; it then archives `~/.claude/hooks` on the next run.

`init.sh` and the launcher's repo sync refuse to install from a checkout whose HEAD is older than the commit recorded in `~/.megavibe/version` (a working copy left on an old branch would overwrite newer hooks and rules): `init.sh` exits 1 naming the three ways out, the launcher skips its repo sync for that launch with one stderr line, and `MEGAVIBE_INIT_ALLOW_STALE=1` overrides both (per run, not remembered). The version compared is the one recorded at install or update, so it moves only then. Not a git tree, an unknown or non-commit version, and equal, newer or diverged checkouts install as before.

| Personal overrides | `CLAUDE.local.md` |
| Deliverables and live decisions | `megavibe-deliverables/` (gitignored) |

## Performance

Megavibe adds minimal overhead. The main cost is the poma-memory vector search database, which stores embeddings of your `.agent/` files locally.

**Real measurements** from an active project (megavibe itself — 1,500-line context log, 50+ sessions, 3,000 chunks indexed):

| Metric | Value | Notes |
|--------|-------|-------|
| **Disk (DB)** | ~10 MB | Scales linearly with indexed content (~3 KB/chunk) |
| **Disk (.agent/)** | ~25 MB | Includes FULL_CONTEXT.md, logs, sessions. Grows over weeks/months |
| **RAM (model)** | ~25 MB | model2vec embedding model, loaded on first search |
| **Search (cold)** | ~500 ms | First search loads the model |
| **Search (warm)** | ~300 ms | Subsequent searches in the same session |
| **Hook overhead** | < 10 ms | Hooks are shell scripts, no network calls |

For a typical project (shorter context, ~500 chunks), expect ~1 MB disk and sub-100ms warm search.

poma-memory uses brute-force cosine similarity on numpy arrays — no external vector DB needed. This scales comfortably to ~10K chunks (~30 MB DB) before you'd notice any slowdown. Most projects will never reach that.

## Updating

Re-run the installer. It's idempotent:

```bash
curl -fsSL https://raw.githubusercontent.com/poma-ai/megavibe/main/install.sh | bash
```

Or if you have a local clone: `bash megavibe/setup.sh`

`megavibe update` (which `/megavibe-restart` also runs) has two arms. On a copy installed by `install.sh` it downloads the latest version and runs its `setup.sh --update`: no questions at all, not "Automatic or Custom?", not "Install X?", not the login pause, not the Gemini key, no sudo password, no Homebrew, pip, git or npx confirmation (their non-interactive switches are set for the run, and an update installs no OS package for the optional Python/pip bootstrap, since dpkg's conffile question has no environment switch), so the setup phase of a restart never stops on a prompt, also over Remote Control. What this does not cover: a broken install, where a required tool is missing altogether (setup then re-runs that tool's own installer, with its own behaviour), and a sign-in a tool asks for on its own at launch. Update mode refreshes what is installed and leaves out what was never chosen on a Custom install (Codex, Gemini, the Playwright MCP server); `bash setup.sh` without the flag is the way to add one later. (Separately, the launcher's once-a-day background `npm i -g` keeps the Codex and Gemini CLIs current; it predates update mode and does not consult that choice.) On a git clone of this repo, `megavibe update` only fast-forwards the checkout: changes apply on the next launch, and `setup.sh` is not run.

**Restart open sessions.** An update takes effect in each session after it restarts.
`megavibe restart-all [--dry-run] [--others]` reports live recorded sessions,
with its name, full project directory, readable tmux pane location, exact manual
restart command, skip reason and final counts. tmux is optional; location queries
never start a server. **Automatic pane input has
been removed.** tmux cannot atomically verify Claude's process identity,
foreground group and entire empty editor while submitting `/exit`. A snapshot
or an opt-in armed marker cannot exclude a later user edit or foreground change.
The command never sends keys, signals, prepares a handover or claims a restart.
`--others` excludes the calling session; otherwise it is reported last.

Type `/megavibe-restart` inside each session you want to restart, then type
`/exit` yourself. It saves `.agent/sessions/<session id>/restart-handover.txt`.
The launcher re-executes its updated copy with `--resume <session id>`, including
when already resumed. **Unknown IDs are skipped**, with a one-line notice;
we removed the old single-session `--continue` fallback too. Shared legacy
markers are ignored. A launcher predating scoped markers requires one manual
restart before this feature can be used.

Handovers record task IDs, numeric start times, bounded local output paths,
and observed process PIDs, start times and executable identifiers (at most
256 characters). **All command arguments and registry command/description
text are omitted**, which also removes secret option values, assignments,
authorization headers and URL userinfo. Environment values are never recorded.
Restart files are owner-only. Do not put credentials in authored notes.

Process observation runs only during an explicit capture, never on ordinary
Stop hooks. Restart-specific task metadata is retained only while this session
has an explicit restart request. At SessionEnd,
the helper refreshes machine evidence while preserving authored notes about
purposes, scheduled prompts, heartbeats and work that cannot be attributed
from process ancestry. A child is labelled “expected to end with the session”;
a previously observed detached process is labelled “may survive (not verified)”.
Neither label proves survival. Missing processes are dropped from the fresh
capture; unknown or unavailable evidence is reported as such.

A capture starts as `not-restarted`; cancellation retains the handover but
cannot activate a reminder. One request record binds its generation, wrapper
identity, owning Claude PID and session ID. Only that Claude process can capture
or cancel it; `/clear` in that process cancels with a notice. A matching successful
exit capture and confirmed process exit allow the launcher to attempt replacement.
The capture stays `not-restarted` until the matching replacement SessionStart
confirms pickup. A failed launch cannot deliver a reminder on a later manual resume. New requests discard old process
attribution, and refreshed handovers archive earlier files. On startup/resume,
the hook delivers the handover once, or a bounded summary with the observation
count and full file path when it is too large. It marks the generation shown
only after writing the full message or summary successfully. Delivery uses
atomic, generation-scoped PID/start-time claims without requiring Python;
retries skip dead owners without deleting claims that another retry could
be using. Failed delivery leaves the reminder available and reports the
handover path on stderr. The reminder
asks the model to verify each PID/start time and actual survival before
re-arming or restarting anything, and to say what it dropped.

**What changed?** `megavibe update` (which `/megavibe-restart` also runs) writes a short plain-language note of what the update changed, so the next session can show it. At update time it makes one call, `claude -p --model haiku --output-format json`, over the commit messages of the range: no tools, no settings or hooks (so no `apiKeyHelper` is loaded either), no MCP servers, a scratch working directory, and the variables that would point it at an API key or another provider (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, the Bedrock, Vertex and Foundry switches) removed, so it uses your subscription. If your Claude login itself is a console API key, the call is billed to it: a few thousand Haiku tokens per update. `MEGAVIBE_UPDATE_SUMMARY=0` turns the call off. The wait is at most 25 seconds by default; `MEGAVIBE_UPDATE_SUMMARY_TIMEOUT=<seconds>` takes one to three digits and is clamped to 1-120, anything else means 25. An answer that is not one complete, successful JSON document (an error, a login message, a truncated or doubled output) is never used as a note.

Records are kept as one file per update, `~/.megavibe/update-notes/<old8>-<new8>`, written whole and never touched again by the launcher, so updates that finish out of order, or that follow one another before you open a session, are separate files and none overwrites another. A range is published at most once, even if two `megavibe update` runs race on it: before publishing, the launcher takes an empty marker directory for the range (`update-notes/.published/<old8>-<new8>`, removed by the hook after 30 days), so a record that was already shown cannot come back. At session start in a megavibe project, `announce-update.sh` (a SessionStart hook, which never waits for an update in progress) takes each pending file with its own atomic move and shows what it got as one start-up message, oldest first by when the update started, capped at about 40 lines and 3000 bytes; what does not fit (and everything beyond the 50 oldest pending records) waits for the next session and is counted in a closing "... and N more updates" line. Each record is shown once, by exactly one session. Nothing is typed into the session for you and the model is not handed the update log. A record shows its note or, when no note could be made (no `claude`, `perl` or `jq` on the machine, a timeout, any error, or a switched-off call), its first few commit subjects. The hook needs `jq` to build the message: without it nothing is shown and the records wait. A record no session has shown for a week is deleted lazily, at the next session start after that, not on a timer. The single `~/.megavibe/.update-changelog` file of older launchers is still read, once.

## Troubleshooting

**`megavibe: command not found`**
```bash
# Add ~/.local/bin to your PATH (add to ~/.zshrc, ~/.bashrc, or ~/.profile)
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc
```

**Hooks aren't firing** — Install jq: `brew install jq` (macOS), `sudo apt install jq` (Ubuntu), `sudo dnf install jq` (Fedora)

**Codex not connecting** — Run `codex` directly to re-authenticate. **Gemini not connecting** — check that `GEMINI_API_KEY` is exported and `~/.gemini/settings.json` has `security.auth.selectedType = "gemini-api-key"` (Google-account login was retired June 18, 2026). Megavibe works without either.

**Context recovery not working** — Check that `.agent/FULL_CONTEXT.md` has content. If empty, the watcher hasn't flushed yet (cycles every 5 min by default) or it isn't running. Verify with `tmux ls | grep '^mvw-'`; tail its log at `.agent/LOGS/watcher.<sid12>.log`. If the watcher is off (`MEGAVIBE_WATCHER=0`), the safety-net hook nudges Claude to flush manually after the first few tool calls.

**poma-memory search not working** — Check Python deps: `python3 -c "import numpy, model2vec"`. If missing: `pip3 install numpy model2vec`

**Memory recall returns stale or off-topic hits** — An older index can be stale (built against a prior checkout) or cross-project-contaminated (an early `poma-memory index` run from a parent dir swept sibling `.agent/` dirs into one db). `poma-memory index` is additive and won't clear that. **Self-heal:** re-run `bash ~/.megavibe/setup.sh` (upgrades poma-memory to ≥0.3.7) and `bash ~/.megavibe/init.sh <project>` (or `/megavibe-restart`) — init does a one-time clean rebuild of that project's index, gated on `.agent/LOGS/.poma-heal-v1`. Force a re-heal anytime by deleting that marker and re-running init, or manually: `rm -f .agent/.poma-memory.db*; poma-memory index .agent/` from inside the project. **Never** run `poma-memory index` from a parent dir containing sub-project `.agent/` dirs — that is what causes the contamination.

**Debug hooks** — `claude --debug` shows hook execution details.

## FAQ

**Does this work with any language/framework?**
Yes. Megavibe is language-agnostic — it's just files and shell hooks.

**Can my team use it on the same project?**
Yes. `.agent/` files are designed for concurrent access. Commit `.agent/` to git so the team shares decisions and lessons.

**Does this replace Claude Code's built-in memory?**
No, it complements it. Claude's auto-memory handles cross-session preferences. Megavibe handles detailed project context, decisions, and task state.

**What if I don't have Gemini or ChatGPT?**
Megavibe still works. Context recovery and reviews fall back to built-in Claude subagents on the same subscription. External backends improve quality but are never required.

**How do I uninstall?**
```bash
rm -rf ~/.megavibe ~/.local/bin/megavibe
# Remove the megavibe block from ~/.claude/CLAUDE.md (between <!-- megavibe-v3 --> markers)
# In each project: rm -rf .agent .claude/hooks .claude/rules .claude/skills CLAUDE.local.md
```

## Architecture (for contributors)

See [CLAUDE.md](CLAUDE.md) for full contributor documentation.

**Running the launcher from a work copy.** Session launches and mutating
subcommands require the installed runtime. After resolving symlinks, the running
launcher and `$MEGAVIBE_HOME/megavibe` must be the same file (`-ef`) in the same
physical directory, with no `.git` directory or file beside them. Pointing
`MEGAVIBE_HOME` at a checkout cannot make it an installation. Case aliases on
case-insensitive filesystems and installed symlinks work; equal-content copies
and hard links from another directory are refused, since that directory could
supply different relative runtime resources.

Both the downloaded installer and `bash megavibe/setup.sh` from a clone use
setup's selective copies into `$HOME/.megavibe`; neither copies the source
`.git`. Setup currently fixes that destination; a runtime relocated to a custom
`MEGAVIBE_HOME` follows the same identity rule. A checkout at the installation
path remains a work copy. Install deliberately with `bash megavibe/setup.sh`.
If you cloned into the installation directory, move that directory to a separate
checkout, copy it back to the installation path without `.git` to keep existing
runtime data, then run `bash /path/to/checkout/setup.sh`.
Both automatic setup branches refuse nonterminal stdin and print an explicit
setup command. Explicit `update` and `setup.sh` keep their behavior.

| Command | Work-copy policy |
|---|---|
| Session launches (including resume/continue) | Guarded |
| `memory set`, `memory unset`, `reviewers set` | Guarded |
| `worktree NAME [BRANCH]`, `worktree remove NAME` | Guarded |
| `node`, `tick`, `usage` (all forms) | Guarded; avoids duplicating the helpers' argument parsers |
| `route` | Guarded; even preview writes usage caches |
| `assistant`, `personal`, `trash-greenlight` | Guarded |
| `update`, `update --check` | Exempt intentionally, including their existing writes |
| `help`, `version` (and flags), `doctor`, `auth`, `sessions`, `restart-all` | Exempt; informational/reporting |
| `remote`, `nondev`, `megawork` | Exempt; print-only notices |
| `reviewers` without `set`, `memory` without `set`/`unset`, `worktree`/`worktree list` | Exempt; listings (invalid forms only print usage) |

For end-to-end tests, `HOME`, `MEGAVIBE_HOME`, and `CLAUDE_CONFIG_DIR` must **all**
point into scratch, with stub `claude`, `tmux`, and network/tool installers first
on `PATH` (stub `git` when testing updates). A scratch config alone is not
isolation: setup uses `$HOME/.megavibe` and the protocol uses `$HOME/.claude`.
To exercise mutating commands or a full launch, copy the launcher and its needed
files into the scratch installation without `.git`. No test-only guard bypass
is needed.

- **Idempotency is sacred.** Both `setup.sh` and `init.sh` are safe to re-run.
- **Marker-based protocol updates.** `<!-- megavibe-v3 -->` markers enable surgical replacement.
- **Infrastructure vs. user data.** Hooks/rules/skills are always overwritten. Context files are never overwritten.
- **Session isolation.** Multiple Claude sessions can run on the same project safely.
- **Remote Control by default.** Every session launches with `--remote-control`.
