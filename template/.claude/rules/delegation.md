# Tool Routing and Delegation Protocols

## Universal fallback principle

**Megavibe works with ONLY a Claude Code subscription.** External backends (Codex, Gemini) improve quality for specific tasks but are never required. Every task has a last-resort path through Claude itself (via the `summarizer` subagent at `.claude/agents/summarizer.md`).

**The standard chain, for every task** (`~/.megavibe/scripts/reviewers.sh digest-chain` prints availability and failure fallback defaults for non-review work on this machine; the list below is the full set, Gemini applies only as the next paragraph says):
1. **Codex** — `~/.megavibe/scripts/codex-review.sh --prompt "..." FILE...` (NOT an MCP server — see below). For a summarising job add `--effort low`; for a review leave `--effort` off and let the user's own `~/.codex/config.toml` choose, but **pass `--timeout 600`** (double the script's 300s default; a large review run in the BACKGROUND, as you should any long job, can pass more, since a foreground Bash call cannot outlast 600s). Add `--model` only if you are prepared to re-run without it when that model is not on this plan: a pinned name that a plan does not expose fails every call and pushes the work to the Claude subagent's 125K tokens.
2. **Claude subagent** — `.claude/agents/summarizer.md`, no key, always available, and the best output of the three on a context digest. It spends the same subscription quota the session runs on, which the allocation rule below weighs.
3. **Gemini** — `~/.megavibe/scripts/gemini-review.sh --prompt "..." FILE...` (requires `$GEMINI_API_KEY` from a **billed** project — Google-account OAuth was retired 2026-06-18, and the free tier is 20 req/day and trains on prompts). Every token is billed and on reviews it is the weakest of the three, so it is last.
4. Gemini MCP (`mcp__gemini-cli__ask-gemini`) — short interactive questions only; the CLI it wraps hardcodes 3.x thinking, so long answers truncate or take minutes.

**Without Codex, Gemini is the (metered) alternative for non-review work — and only then.** Added 2026-10-08 after finding teammates with no Codex at all, for whom every re-hydration otherwise cost ~125K tokens of their own Claude quota. `reviewers.sh digest-chain` prints `codex subagent` where `codex exec` works (or the probe cannot tell), `gemini subagent` where it answered "unusable" and a `$GEMINI_API_KEY` is set, and `subagent` otherwise; the Claude subagent is printed last; allocation below chooses the first backend among those available. On a machine WITH Codex, `gemini-review.sh` refuses general (non-`--as-reviewer`) calls outright (exit 4; `MEGAVIBE_GEMINI_DIGEST=1` overrides), so Gemini cannot quietly become a third paid path. Where it is allowed, every call is rationed by the script itself, not by this text: flash-lite at thinkingLevel low only (a `--pro` or `--auto` outside a review is downgraded), output capped at 12000 tokens and input at 300 KB, at most 40 general calls and an estimated $1.00 per local day (`MEGAVIBE_GEMINI_DAILY_CALLS`, `MEGAVIBE_GEMINI_DAILY_USD`, `MEGAVIBE_GEMINI_MAX_INPUT_KB`, `MEGAVIBE_GEMINI_MAX_OUT`; a daily cap of 0 or an unreadable value switches general use off). Each call is reserved in the ledger under a lock BEFORE it is sent (a call that fails after sending still counts) and an unreadable or unwritable ledger refuses; the context watcher may use at most 60% of the day so `/rehydrate` keeps a share; the lock needs `perl`, without it general calls refuse and `digest-chain` does not advertise Gemini, exit 5 when a cap is hit so the caller falls through to the subagent, and every call logged to `~/.megavibe/gemini-usage.jsonl` (`gemini-review.sh --budget` shows today's). The context watcher — the heaviest recurring caller — goes through the same script and flushes at half rate while Gemini is its backend. Reviews are never refused by these caps (a skipped review is worse than a spent cent) but are logged and count toward the day's spend. The dollar figure is an estimate priced on the high side (`MEGAVIBE_GEMINI_PRICES` tunes it), not a bill; the API key's own project budget is the real ceiling.

**Subscription usage steers the main thread and subagent pinning, never the review floor.** `megavibe` reads the Claude usage history the statusline keeps (`scripts/usage-route.sh`) and, on a fresh launch with no explicit `--model`/`--effort` and no model or effort pinned by the environment or project settings (each half separately), starts an over-used account on `sonnet`/`medium` and an under-used one (capacity that will reset unspent) on `opus` (Max plans only; a lower or unknown plan keeps its own choice); a `usage router:` line from `usage-advisory.sh` says once per band how to pin subagents (`haiku`/`sonnet` when hot, inherit when capacity would be wasted). It does not change the reviewer tiers below: the `reviewer` subagent stays pinned; provider choice follows the continuous allocation rule below. API billing is barred at launch (`MEGAVIBE_ALLOW_API_BILLING=1` to accept). Codex gets the same bands from its own weekly rate-limit records (`usage-route.sh codex`), as advice: no band changes a review's effort (the automatic `xhigh` was removed on 2026-10-11 after it timed out on real large reviews and a blind benchmark found it no better). `usage-route.sh balance` tells the session which subscription optional work should lean on when the two projections differ by 20 points or more, or one runs hot. It is advice; `digest-chain` and the review tiers are not touched.

**Allocation is gradual and continuous (added 2026-11-01).** At EVERY allocation point — each review reader, delta check, fix round, implementation agent, memo, re-hydration, digest and second opinion — re-read both weekly windows (`MEGAVIBE_ROUTER_PROVIDER=claude usage-route.sh status --peek` and the same with `codex`: used, projection, time to reset, staleness; a missing projection is unknown, never spare capacity). Weigh that unit's estimated consumption on each subscription and give it to the available subscription whose projected end-of-window use is further below its limit, so the two projections converge and both land just under 100% at their respective resets; state the allocation in one line. Re-decide for every unit, including each reader and each implementation or fix round: use Claude agents or `codex exec -s workspace-write -C <worktree>` by the same weighing. A batch plan or a router band is not a substitute for this continuous allocation; `balance` only gives an optional-work preference and omits projections in several cases. **Hard backstop:** a subscription whose projection is at or over its limit gets no work the other can do; this is the fallback, not the trigger for balancing.

This weighing governs provider choice throughout this file, including the primary/fallback defaults below; preserve availability, reviewer allow-lists, Gemini's restrictions and the review floor. With only Claude, work continues through Claude and its subagents. Reserve capacity for required review; when a usable projection plus estimated demand leaves no capacity after weighing alternatives, defer optional work until reset and say what and until when. If the allocated ship readers cannot complete the round under the availability/failure floor below, the whole round waits and shipping stays blocked; a documented single-subagent floor is a complete round for that configuration. Agents already running are never stopped to rebalance. Parallel Codex calls need no second account or login: launch each with the Bash tool's `run_in_background` and its own heartbeat, never a bare `&`. The main thread's model and effort can be switched mid-session with `/model` and `/effort`; no restart is needed.

**Reasoning-effort/timeout asymmetry, found and fixed 2026-10-04.** `~/.codex/config.toml` had `model_reasoning_effort = "low"` while the Claude `reviewer` subagent ran `medium` (now `high`) — Codex, the *primary* reviewer by call volume, was configured to think less than its own fallback. Measured over September: of 1,015 `codex-review.sh`/`gemini-review.sh` calls, ~21.3% actually failed (10.5% timeout at the 300s default, 10.8% error — separate from the 1.9% that exited 4 as a deliberate `MEGAVIBE_REVIEWERS` skip, which is a setting, not a failure, and does not trigger a reviewer-fallback report). Each real failure on a review call falls through to the costlier Sonnet `reviewer` per the protocol's own fallback rule, which both inflates Claude spend and quietly erases the intended Codex-first ordering; non-review Codex calls (re-hydration) fall through to the `summarizer` subagent instead, per the chain above — research is the documented exception (Gemini stays ahead of the subagent there; see the Research memo section below). Bumped `model_reasoning_effort` to `high` directly in `~/.codex/config.toml` (a personal file, not this repo) and smoke-tested at the new setting: a small single-file review ran in 21s, well inside even the old 300s cap — but that was a trivial task, and real multi-file reviews that run tests will run longer at higher effort, which is why the timeout above doubled too. `~/.codex/sessions/` shows real, growing Codex usage (not idle) but at roughly 7% of Claude's measured call volume over the same window — directional evidence of headroom, not a measured quota ceiling, since one `codex exec` call can cover what several Claude turns do. A/B'd once since (2026-10-05): `gpt-6.1-sol` vs. `gpt-6-astra`, both at `high` effort, same real review task. Same ship verdict, comparable depth, astra marginally faster this run. No clear win on n=1 — kept `sol` as the default rather than switch on a tie. The backend comparison above measured summarisation, not review quality, and explicitly found astra's longer summary wasn't a more accurate one, so that comparison doesn't carry over; revisit the model choice if more review trials show a consistent gap either way.

**Why this order, measured 2026-09-18.** Same 196 KB re-hydration input, four backends in parallel:

| Backend | Time | Output | What it costs |
|---|---|---|---|
| Codex `gpt-5.6-terra`, effort low | 23 s | 76 lines | plan tokens |
| Claude `summarizer` (sonnet) | 87 s | 64 lines | 125K tokens of this session's own subscription |
| Codex `gpt-6-astra`, effort low / high | 93 / 105 s | 156 / 168 lines | plan tokens |
| Gemini `3.1-flash-lite`, level low | 9 s | 40 lines | billed per token |
| Claude `general-purpose` + `model: haiku`, measured 2026-10-04 on a different 200KB input | 65 s | 108 lines, specific (named commits, PR #s, task IDs, acceptance criteria — plus a self-added Rationale section not in the template) | 113K tokens of this session's own subscription — *less* than the sonnet subagent, at half Sonnet's per-token price |

Nothing was invented by any of them — every claim traced back to the input. Line count doesn't rank them: the subagent's 64 lines carried the most specifics per line (named commits, task IDs, open blockers), the judgement behind ranking it above Gemini. Two conclusions: **effort is the wrong knob for summarising** (even at `high`, Codex spent only 94 reasoning tokens — digesting a log doesn't reason, the model sets time and length), and **a bigger model isn't a better summary** (astra took 4x the wall-clock for a longer document, not a more accurate one).

**A third conclusion, from the Haiku row above: a smaller model isn't a worse summary either, at least once.** Haiku's output matched the sonnet subagent's named-specifics density (commits, PR numbers, task IDs, acceptance criteria) at half Sonnet's per-token price and fewer total tokens, with one self-corrected hiccup (1 of 4 Read calls errored, presumably a chunk-boundary miss, and it recovered without being told to). This is **n=1 on a single real input, not a repeat of the controlled 4-way test above** — the original input file no longer exists to re-run it on. `summarizer.md` stays pinned to `sonnet` until a second run confirms this isn't a fluke; `general-purpose` + `model: haiku` is worth reaching for directly on read-and-summarize tasks with no judgment call in them (a context digest, not a decision) in the meantime.

**A Codex quota day is the weakest configuration megavibe has.** Reviews, re-hydration and the watcher's five-minute flush all draw on the same subscription; on the day these numbers were measured, Codex was exhausted for ~3 hours, leaving reviews to the `reviewer` subagent plus `gemini-review.sh --as-reviewer --fallback --pro` — the same audit recorded Gemini alone approving five changes with real blockers. On a quota day: **treat every Gemini finding as a lead to reproduce and every Gemini verdict as unverified**, say so in the synthesis, and prefer holding a risky merge over shipping on one unreproduced review. `megavibe reviewers set all` pays for the third opinion every day instead of relying on it only when the primary is down.

**Reviews rank differently — depth is the point.** Codex reads the repo, runs tests, reproduces failures; over 11 paired reviews in one day it found real defects in every unit. Gemini — one stateless call over inlined files — produced four wrong headline findings and five SHIP verdicts on code with confirmed blockers (one "a masterclass" on a patch with a P1 in it). That's why it's the fallback, not a third opinion, and why it always gets `--pro` when it reviews.

**There is no Codex MCP server, since codex-cli 0.154.0 (2026-09-10).** That release deleted the `mcp-server` subcommand — `strings` on the native binary returns zero occurrences, so it is gone from compiled code, not just from help; `codex mcp` now manages Codex as a *client* (list/get/add/remove/login/logout). Do not try to register it, and do not read `CONNECTION_CLOSED` from a `codex` MCP entry as a network fault: codex forwards an unrecognised subcommand to the interactive CLI as a prompt, the TUI starts, dies with "stdin is not a terminal", and the pipe closes mid-handshake. The error never names the real cause, which is why this read as an outage for hours. `setup.sh` removes the dead registration; `on-session-start.sh` asserts `codex exec` exists rather than assuming it.

**Use `~/.megavibe/scripts/codex-review.sh`**, which mirrors `gemini-review.sh`'s interface: `--prompt`/`--prompt-file` plus `FILE...`, files appended as `===== path =====` blocks, `--out`, `--model`, `--timeout` (default 300s, exit 124 on timeout so the chain falls through instead of hanging). The project under review is never writable and there is **no `--sandbox` flag** — passing one is refused (exit 2), as are `--approve-for-me`, `--full-auto` and `--dangerously-bypass-approvals-and-sandbox`. Under `--as-reviewer` Codex runs with a throwaway **scratch directory** as its working directory (writable, `TMPDIR` inside it, deleted on exit; network off; `/tmp` and the project read-only, measured with a canary file), so it can write and run the harnesses a review needs: until 2026-10-15 the sandbox was strictly read-only and 22 of 23 reviews in one session said they could not create a scratch file and reviewed by reading, which is the "reviewer that only reads the diff" failure this protocol names. Both modes also pass `--ignore-rules`: a user's codex exec-policy rules (`$CODEX_HOME/rules`, which codex writes when someone answers "always allow") run an allowed command outside any sandbox and re-opened the project, `$HOME`, `/tmp` and the network (found 2026-10-15 with the real codex, in strict mode too). Not covered: a `notify` command or MCP server in the user's own codex config runs as part of codex itself. `--strict` or `MEGAVIBE_CODEX_SCRATCH=0` restores a fully read-only run; the non-review uses (`/rehydrate`, summaries, memos) stay strict, `--scratch` opts them in. `exec` has no interactive approver, and the wrapper pins `approval_policy="never"` so a user's on-request or auto-review setting cannot approve an escalation; the elicitation problem that `codex-approval-never.sh` existed for cannot arise. That hook is therefore gone from the template and from new projects; existing projects keep an inert copy, since pruning it would mean a settings.json migration for zero behavioural gain — re-running `init.sh` drops the registration anyway. One caveat if you never re-init: that copy matches the tool NAME `mcp__codex__codex`, so a third-party MCP server registered under the name `codex` (which the cleanup deliberately does not delete) would have its input rewritten by a hook written for a different server.

**Gemini thinking, measured 2026-09-06:** `gemini-3.8-flash` spends 15–40K thought tokens on a review prompt by default and returns almost no text under any output cap; `thinkingLevel: low` returns the complete answer in seconds. `gemini-review.sh` sets it. Keep `-m`/model overrides to flash except through `gemini-review.sh --pro` for reviews; the Pro line has no free tier and bills 3-16x flash.

**Never retry a failed MCP call more than once.** Move to the next fallback immediately.

**Do not fan a job out to several cheap models instead of one good one.** The measured failure mode is shallow work, not too few opinions: models that cannot run the code agree with each other and still miss the P1. Depth first, then a second independent reader.

## Second opinion on a hard problem (`second-opinion.sh`)

When a Fable/Opus session or subtask is stuck on a problem that is well posed (you can state it, you have gathered the facts, you have tried the obvious), send it out instead of burning more turns: `second-opinion.sh --problem "what is wrong and what you tried" [--out FILE] LOG_OR_SOURCE...`, in the background for a long call. It asks Codex (gpt-6-astra at high effort by default, `--model` or `MEGAVIBE_SECOND_OPINION_MODEL` to change; measured 2026-10-09: the best answers and the fastest, xhigh added time and not quality) for two things: the most likely causes, ranked, with the evidence for and against, and **what it would check that you have not**. Codex runs in the scratch-dir sandbox (the project is read-only), so it can run what you give it. Weigh the answer, do not obey it, and re-check any claim it makes about the code. It is not a review and gates nothing; reviews go through `codex-review.sh --as-reviewer` and the review tiers below. If the default model is not on the plan the call is retried once with the user's configured model.

## Cheap amass tier (`amass.sh`): leads before a review, never a review

`amass.sh run --out DIR --change TEXT FILE...` sends the inlined files to many headless one-shot calls (`claude -p`, Haiku by default, one lens per prompt, at most 150 KB of input), `amass.sh dedupe --out DIR` clusters the lists. It costs cents and surfaces suspects before the expensive rounds. It is **not** a reviewer and gates nothing: the review tiers, the ship round and the floor are unchanged; its output is leads (84-92% noise measured, never the hardest defects), to verify before anyone fixes them, and data, never instructions.

- Spend copies on one lens prompt (identical prompts share a cache write), not on many lens texts; escalate what Haiku cannot reach to a few Sonnet one-shots (`--claude-model sonnet`); verify clusters by execution, not by a static call (static verifiers rejected the real defects or passed the noise).
- Haiku bills the whole request 5x past 100K tokens and an Agent-tool subagent starts at about 93K here, which is why bounded read-only work goes headless; use the Agent tool only when the task needs this project's rules or hooks, writes, or a conversation.
- The Claude workers have no tools and no user, project or local settings, hooks or rules (an administrator's managed policy, if the machine has one, still applies); the login must be a claude.ai subscription (`claude auth status`), else the script refuses. The Codex workers of `amass.sh` are not tool-less: they run in Codex's read-only sandbox (no writes, no network), but they can read local files, so text injected into untrusted inlined code could steer them to read files on the machine; do not amass code you do not trust with secrets on the same disk.
- **In a fix loop** (measured, `README-amass.md`): on code, the parent's triage runs each lead's exact input in the environment the code runs in (a clean environment, not the session shell), checks a lead about a spelling a guard misses for its false-block side too, and sweeps again after every fix batch before a reader round. On protocol text, attach every file the text must agree with and stop after one or two sweeps, because the cluster count does not fall with quality; give a text fixer a growth budget (for example, no net growth); and when one added section draws findings in every round, offer cutting it as an option at the churn pause instead of rewording it again.

Measurements, prices, cliffs and limits: **`README-amass.md`**.

## Both providers, in every shape: allocation and spawn paths

Every unit of work (a review reader, a fix round, an implementation, a digest, a second opinion) can go to either subscription, and the continuous allocation rule above decides it by weighing both windows each time:
- **Claude tool-less and Codex read-only, lean:** `amass.sh` mixes Claude (Haiku) and Codex (luna) calls in one run, split inversely to each subscription's projected usage (`--provider auto`, the default; details in `README-amass.md`), for suspect enumeration and deduplication only (its parser accepts finding-formatted output, so a prose digest fails); digests and other work go to the `summarizer` or an Agent-tool subagent until a general headless transport exists.
- **Claude, lean, with tools:** `claude-review.sh --tools none|read|exec` (the default under `--as-reviewer` is exec): a throwaway scratch directory, writes confined by a macOS seatbelt, the guard hooks registered, none of this project's rules loaded, about 5-8K tokens of context; it needs a claude.ai subscription login. With `--as-reviewer` it is a Claude reader (see non-negotiable 4 of `CLAUDE.md`).
- **Claude, Agent tool:** the subagent inherits this project's whole instruction stack (about 93K tokens here), so pin `model:` and use it where the task needs the rules, hooks, writes or the conversation; it is the Claude reader for reviews that need this project's rules, hooks or conversation, and the fallback when the lean worker cannot run.
- **Codex:** `codex-review.sh` (reviews: always `--as-reviewer`, never raw `codex exec`); `codex exec -s workspace-write -C <worktree>` only for implementation and fix rounds.

How much weighing a call is worth follows its price class: calls in the Haiku or luna class ($0.10/$0.50 per million) may stay on whichever side is convenient; for Sonnet, Opus and Fable against terra, sol and astra, never default to one side by habit, and state the allocation in one line each time. Every `amass.sh run` and `dedupe` call that reaches the model appends a line to `~/.megavibe/amass-usage.jsonl` (best effort); compare it with the Agent-tool calls in the transcripts to see whether this is followed.

## Two review tiers, and why

Every intermediate round gets **one** reviewer — Codex or the `reviewer` subagent, selected by continuous weighing among eligible backends, with the subagent replacing an absent, switched-off or failed Codex (Gemini may join that round, never take it alone). The round that gates the ship normally requires two independent readers that actually reviewed the final candidate in full, **in parallel**, allocated as below, plus available Gemini when pinned as a peer; the availability/failure floor below is the explicit exception. Intermediate rounds need only one reader, critical work included. Critical means credentials or security, data loss or destructive paths, anything public or user-facing, the protocol and templates themselves, and anything the user names: such work is held to the same ship round and is the work for which a missing or failed review is least acceptable, but it does not get a second reader on rounds that are still moving.

The reason is cost asymmetry, measured. Codex draws on a separate plan; the `reviewer` subagent draws ~180-200K tokens of the SAME subscription the session is spending — in one session here, two invocations cost 386K tokens (measured at `effort: medium`; `effort: high` costs more per invocation, deliberately — see below). Running both on every intermediate round spends the user's Claude subscription quota (a different resource from the session's context window, and the one that runs out) to re-check work that is still moving. Running only Codex on the last round ships on a single unreproduced opinion.

**`effort: high`, not `medium` (changed 2026-10-04).** Measured across all projects for the month of September: the whole Sonnet-pinned reviewer+summarizer track was ~4% of total Claude spend ($326 of ~$8,400, list-price estimate) — the dominant costs were main-thread model choice and *unpinned* generic subagents (Explore/Plan/general-purpose riding the parent session's model — see `spinouts.md`), not this track. Raising the reviewer's effort increases its token spend per invocation, but against a base that small the absolute cost stays trivial, and review is the one place in the protocol where under-thinking directly costs a missed blocker. No controlled A/B exists comparing medium vs. high review quality here — if one gets built later (same diff, both effort levels, findings diffed against a known-blocker set), record it and revisit. Until then this is a deliberate quality-over-cost call given the measured cost floor, not a measured win.

The honest cost of this trade: an intermediate reviewer's mistake can shape the implementation and the framing of the next review, and the ship round may miss it again — especially if it is shown only the latest fixes rather than the whole candidate. That is why the ship round reviews the **final candidate in full**, not the delta since the last round. "Round one's defect gets caught later" is the expectation, not a guarantee.

Iterating toward a fix is a normal round. The last one before merge is not. A change that goes through exactly one review round is having its ship round, so it gets the full allocated set defined below.

**Decide the tier before the round, not after.** Nothing ships on an intermediate review: before merging, deploying, publishing or calling an important result done, the final candidate must have had a full-set review. For a follow-up after a completed full-set review, apply the verification-only test of non-negotiable 4; its conditions live there only, so the two copies cannot drift, and its other stated exceptions apply as written there. Any substantive, uncertain or critical change requires independent review before shipping. If a round you started as "normal" turns out to be the last, run the missing reviewers on the final state first. Otherwise a change can be reviewed cheaply forever and then merged on the strength of a round that was never the gate.

**Measured 2026-10-09, and the decision it led to.** Across 31 paired rounds in six sessions (Codex and the `reviewer` subagent each reviewed the candidate of that round, which evolved between rounds) there were 201 distinct blocker/P1/P2 findings, counted by the analysing agents' judgement of "the same defect", so every percentage below is an observational estimate: about 28% found by both, about 42% by Codex only, about 30% by the subagent only. So Codex alone would have covered about 70% and the subagent alone about 58%: the two are NOT redundant, and a "second only if the first is clean" gate would almost never run it (Codex said "do not ship" in 28 of 31 rounds). The ship round therefore normally keeps two independent readers, with composition chosen by the allocation rule below. The cost side: one 9-round PR spent about 950K Claude tokens on the subagent (about 100K per round measured there; ~180-200K on larger inputs), and from the sixth round on most findings were bugs introduced by the previous round's fixes. The repo owner decided: both readers only on the ship round. Read it as a COST decision, not a yield one: on any intermediate round the second reader's findings (about 30% of the serious ones) are not found then, they surface at the ship round, and a ship round that returns blockers is followed by normal rounds and then a NEW full-set ship round on the final state, so the saving is on the rounds in between. Caveats: the subagent often ran after Codex's fixes had landed (inflating its unique count); the two samples disagree (on one narrow shell change, 7 paired rounds, the subagent alone found 1 of 16 serious findings; on five wider protocol, security and multi-file sessions, 24 paired rounds, it alone found 56 of 185); no transcript contains a higher-effort single reviewer.

**Eligibility is not allocation.** `MEGAVIBE_REVIEWERS` and backend availability determine which backends may review; they do not require every eligible backend to run. The **full allocated set** is the ship readers selected by continuous weighing, plus available Gemini when pinned as a peer, subject to the availability/failure floor below. A "full-set review" means this full allocated set completed its reviews of the final candidate. Count completed reviews, not eligible backends, launched calls or failed calls. Two successful Codex calls on different models count as two readers; they do not require an additional Claude subagent.

**Allocate every ship reader, including the first (added 2026-11-01).** Re-read both weekly windows and weigh each reader's estimated consumption. Normally allocate Codex + the Claude `reviewer` subagent, or two separate Codex calls on different models (for example, `codex-review.sh --as-reviewer --model gpt-6-astra` and `codex-review.sh --as-reviewer --model gpt-6.1-sol`). For the second reader after Codex, choose the subagent when Claude has relatively larger projected headroom, or a different Codex model when Codex has it. If the first reader is the subagent, Codex supplies the second, subject to the floor below. Give every reader the same files and brief, explicitly telling each to review the final candidate in full and adversarially. The 2026-10-09 measurement showed different readers find different things; two Codex models may share more blind spots than Codex + Claude, so prefer the mixed pair when headroom is comparable, without overriding the hard backstop. This is an allocation choice, not a measured yield equivalence.

**Availability/failure floor and backstop symmetry.** At least one independent reviewer must actually run; Gemini never stands alone. When Codex is absent, switched off, fails, or is excluded by the hard backstop (projected use at or over its limit while Claude can do the review), the `reviewer` subagent is the floor, including on the ship round. A failed Codex call is replaced by the subagent; if a subagent already reviewed that final candidate, do not count a repeat run as a second independent reader. Gemini may join on `--pro` only as the existing rules allow: as an eligible, available peer (including the default on a machine without Codex), or with `--fallback` after an actual Codex failure when the allow-list permits it. A projection at the limit or a switched-off Codex is not a failed call and does not unlock Gemini fallback. If no permitted second reader remains, the single subagent satisfies the floor; state the missing reader, reason and resulting shortfall in the synthesis. Conversely, when Claude is excluded by the backstop and Codex can do the work, allocate two different Codex models. Relative headroom alone, below the hard backstop, never justifies a one-reader ship round; if the required readers cannot run and none of these exceptions applies, wait rather than ship. A completed `claude-review.sh --as-reviewer` run satisfies the same floor as a subagent review and counts as that one Claude reader; if it fails or refuses, the subagent takes over, and a subagent and a worker that both reviewed the same final candidate count as one Claude reader, not two independent ones.

**Cut rounds before cutting readers (added 2026-11-11).** In one session, four PRs cost about 22 Codex review calls and 8 implementation runs: the rounds were the expense, not the price of a call. Before a round: fetch and measure the candidate against its intended base, and update a base that is only behind (a fast-forward) following non-negotiables 5 and 6 of `CLAUDE.md`, stop conditions included (a stale base returned findings already fixed on main); run once every claim you wrote about a tool or script (an untested claim cost a whole two-reader round); run `amass.sh` on review input under 150 KB and pass its clusters to the reader as leads to verify by execution, never as a verdict. A step that cannot run (no `amass.sh`, no Codex) is named in the brief and the review round proceeds; a failed fetch or any other stop condition of non-negotiable 6 still stops commit, push and merge, and a claim you could not run is reported as untested. Brief the implementer with a hazard checklist for the class of tool and require a failing-first test per finding: for git tooling, pending operations (rebase, merge, autostash), live locks, submodules, stale remote refs and `origin/HEAD`, case-insensitive paths; for process supervision, the inspection probe failing or blocking, reparenting and pid reuse. Run every new tool once in a scratch copy or dry-run mode before the ship round (never against live state without the user's consent), and give that output to the readers. Fix blocking findings at once, in a new candidate (readers review a frozen copy) that is re-reviewed per non-negotiable 4; a fix that adds behaviour or judgement is reviewed however obvious it looks. When successive rounds keep surfacing new edge cases unrelated to the last fix, or three rounds in a row return only P2s, run an amass sweep (full candidate under 150 KB) before the next intermediate reader round, never instead of the ship round: verify each cluster by execution, fix the confirmed material ones in one batch, record as known gaps only those the materiality bar rates immaterial (a material one blocks), then run the full ship round on the whole final candidate. A related finding that needs the readers' depth stays a reader round; the churn pause stays for recurring blockers. Intermediate rounds use ONE reader; two readers only on the round you believe is the last.

**Brief every reviewer with the materiality bar:** what the real workload is (which inputs, formats, platforms and volumes actually occur) and what effect size would change a decision, so findings can be weighed as non-negotiable 4 requires. Without it a thorough reviewer generates synthetic edge cases round after round and every round returns "do not ship".

**Brief every reviewer (subagent or Codex) with the process rule:** never `pkill`, `killall`, kill by pattern, `tmux` or `launchctl` commands that stop anything; kill only a PID you started yourself. A pattern kill by a reviewer took down the tmux server and every remote-control session on 2026-10-15; `reviewer.md` says it and `block-dangerous-bash.sh` now refuses `pkill`, `killall` and tmux/launchctl stop commands (`MEGAVIBE_ALLOW_KILL=1` is the human's escape hatch). It does not catch `kill $(pgrep ...)`, so kill only `$!`.

**Brief every subagent reviewer with the shell checklist:** call scripts by absolute path; start a Bash call that writes with `cd <scratch dir> || exit 1`; never write under the user's real home, and for tests that write under `$HOME` set `HOME` to a scratch directory as `reviewer.md` says; use fresh directory names instead of `rm -rf`, and remove each round's scratch copy as the deletion rules say. Keep each Bash call short and plain, because an unanswered permission prompt stalls a background subagent. Readers review a frozen copy of the whole candidate, never a tree that is still changing. After each round the parent checks `git status -sb`, the branch, and that the user's config directory was not written.

**The floor is one independent reviewer, never zero.** On a machine with only a Claude subscription, that is the subagent on every round, because there is nothing else — the tiering removes the *second* reader on intermediate rounds, never the only one.

## Switching reviewers off

`MEGAVIBE_REVIEWERS` is an allow-list of reviewer ids — `gemini`, `codex`, and `reviewer` (the Claude subagent, which is **always** in the resolved set and cannot be switched off: it is the floor non-negotiable 4 rests on, costs no key, and has no script to gate it through). Being in the set is about backend eligibility, not reader allocation: the two tiers above decide which readers actually run. Unset, empty or `auto` is the DEFAULT: `reviewer` + `codex` where `codex exec` works, `reviewer` + `gemini` where it does not, and all three if the probe cannot answer at all. `all` names every reviewer explicitly and makes Gemini eligible as a peer — an ordinary intermediate round still runs one reviewer, and ship rounds run the full allocated set defined above in parallel. To pin the set:

```
megavibe reviewers                          # what is on, where it was set, what is available
megavibe reviewers set all                  # all backends eligible; add Gemini to allocated ship readers
megavibe reviewers set reviewer codex       # never gemini, not even as codex's fallback
megavibe reviewers set --project reviewer   # this project only (uncommitted)
megavibe reviewers set auto                 # back to the default
```

`auto` and `all` used to be the same word for the same thing, because the default WAS all three. They are different now, so `set all` writes the literal value instead of clearing the setting. A pin written by the OLD command cannot be recovered — it cleared the setting, which is indistinguishable from never having chosen — so the session-start hook says once, per machine, that the default changed and how to get all three back.

It writes `MEGAVIBE_REVIEWERS` into the `env` block of `~/.claude/settings.json`, or with `--project` into the project's uncommitted `.claude/settings.local.json`, which Claude Code applies to the session so hooks and Bash calls inherit it. `reviewers.sh` also reads those files directly, so a review script run from a plain terminal honours the same setting. Precedence: the exported variable, then `settings.local.json`, then the project's committed `settings.json`, then the user file — except that the committed project file may only **add** reviewers. It arrives with a clone, written by whoever wrote the repo, and a repo that can switch off the reviewers reading its own code is a hole, not a feature; a reducing pin there is ignored with a warning. `~/.megavibe/scripts/reviewers.sh list` prints the resolved set, `source` says which of them supplied it.

**It gates the reviewer ROLE, not the backend.** `gemini-review.sh` and `codex-review.sh` are also the general Codex/Gemini transport — steps 1 and 3 of the fallback chain above, and what `/rehydrate` and `/prune-context` call — so they consult the allow-list **only when the caller passes `--as-reviewer`**. Pass that flag for the reviews of non-negotiable 4 and for nothing else: switching a reviewer off must not cost anyone context recovery. (Separately, and not through `MEGAVIBE_REVIEWERS`: `gemini-review.sh` without `--as-reviewer` is the rationed no-Codex alternative described at the top, and refuses on a machine where Codex is usable.) Getting this backwards is the bug the first cut shipped — `MEGAVIBE_REVIEWERS="reviewer"` silently stripped `/rehydrate` of both external backends.

Allow-list rather than ignore-list on purpose: the config states exactly which backends may review, where an ignore-list only says it relative to whatever happens to be installed on the machine. The cost is that a reviewer added to megavibe later is off for anyone who has pinned a list.

**Every unclear path resolves to MORE review.** A settings file that exists but cannot be parsed — bad JSON, no `jq` — is ambiguous rather than absent, and returns all three. An unrecognised name invalidates the whole pin rather than being dropped from it, because `"gemini codx"` would otherwise switch codex off forever on a typo. A committed project `settings.json` is compared against what the machine would resolve WITHOUT it and ignored if it removes anything, which is why `auto` in a cloned repo cannot quietly take Gemini away from a user whose own file says `all`. The availability probe is bounded and, on a timeout, counts as unknown and returns all three. In the review scripts, exit status **1** from `reviewers.sh` is the only answer that switches a reviewer off; every other status is the helper failing to answer, and the review runs.

Enforcement is in the scripts, not only here — under `--as-reviewer` they exit **4** with a `skip:` line when their reviewer is not in the set, before spending a token. Exit 4 means *switched off*, not *failed*: do not fall through the chain looking for a substitute, and do not report the review as degraded by a backend outage. Every unclear path fails OPEN to all reviewers — unreadable config, missing `jq`, an unrecognised value, a helper that crashes — because reviewing with fewer eyes than the user expects is the bad direction to fail in. A round that ends up with only the `reviewer` subagent is still a review; say so plainly in the synthesis.

**Never override the Gemini model to a Pro variant** (`-m gemini-*-pro*`, `model: gemini-*-pro*`) in the MCP tool, the CLI, or the watcher. Pro has no free tier and bills at 3-16x flash on a paid key. The sanctioned use is `gemini-review.sh --pro` for **any reviewer-role call** — flash truncates or stalls on 3.x thinking specifically for reviews, not just the protocol/template/user-facing subset, matching CLAUDE.md non-negotiable 4's "always `--pro`" for reviews (≈$0.15 a review); everything else — non-review Gemini usage — is pinned by the script to a flash-lite model (`MEGAVIBE_GEMINI_DIGEST_MODEL`, a caller's `--model` is ignored), and if that is not enough there, fall through the chain to the Claude subagent. The `ask-gemini` MCP tool bypasses the cost rails entirely: short interactive questions only. *(Found 2026-10-05: this line previously scoped "sanctioned" too narrowly, contradicting the Tool routing table and non-negotiable 4, both of which already required `--pro` on every reviewer-role Gemini call, review-tier or not — pre-existing, not introduced by the change in this diff.)*

## Cache heartbeat: measured, verdict genuinely unresolved (2026-10-04/05)

Proposed once: ping an idle session every ~50 min (under the 1h ephemeral cache TTL) for up to 12-24h to avoid a cold-cache rebuild. Mechanism is confirmed accurate: every request that touches a cached prefix bills `cache_read_input_tokens` for the FULL prefix length, every time; there is no cheaper standalone way to extend a cache entry's TTL. Of 207 cold-restart events since Sep 1, 177 fall inside a 24h window, totaling 75.9M tokens to rebuild from scratch at resume (raw `cache_creation_input_tokens`). Pinging all 177 every 50 min for the length of each gap, then resuming warm, costs 498.7M raw tokens moved — **6.57x more tokens than doing nothing.**

**What that 6.57x does NOT settle: whether raw token count is the metric that matters.** Anthropic's own published API pricing weights a cache read at roughly 0.1x base input price and a 1-hour cache write at roughly 2x — a 20x asymmetry in the OPPOSITE direction from the raw-token count, because reads are cheap to serve on the backend and writes aren't. If Claude Code's subscription usage/rate limits are cost-weighted the way the dollar pricing is rather than a flat sum of tokens-moved, heartbeating could be net CHEAPER against the real limit, not 6.57x more expensive — a complete reversal. Anthropic's actual plan-metering formula isn't publicly documented, and nothing here verifies which model applies. **Verdict: don't build persistent heartbeat infrastructure on either conclusion yet.** Before deciding either way: run matched trials — several heartbeat-then-resume cycles AND several cold-resume cycles on comparable work, controlling for other activity in the window — and compare what each does to Claude Code's own usage/rate-limit display specifically (not the API response's token counts, and re-fetch it fresh rather than trusting a cached reading — `/usage` can show a stale one). A couple of pings alone only measures the ping's own cost, not whether it actually beat the cold-resume alternative; this section should be rewritten once a real matched comparison exists.

## Gemini / Codex / Claude subagent delegation protocols

These protocols apply to whichever backend is available. Codex is the primary — `~/.megavibe/scripts/codex-review.sh` — then the Claude subagent via the Agent tool with `.claude/agents/summarizer.md`, then Gemini via `~/.megavibe/scripts/gemini-review.sh` (on a machine WITHOUT Codex, Gemini comes before the subagent) (its MCP tool only for short questions). The inputs and output requirements are the same whichever one answers.

### Re-hydration (regenerate working context)

Inputs to provide the backend:
- `.agent/FULL_CONTEXT.md`
- `.agent/DECISIONS.md`
- `.agent/TASKS.md`
- `git status` + `git diff --stat` output

Output requirements (max ~400 lines):
- **Goal** — current objective
- **Constraints** — must-not-break list
- **What's Done** — files touched, changes landed
- **Open Tasks** — with acceptance criteria
- **Risks / Unknowns**
- **Next Actions** — 3 concrete next steps

Rules:
- Never regenerate from an old WORKING_CONTEXT alone. Always re-derive from the full log + repo state.
- Write WORKING_CONTEXT to the session-scoped path (`.agent/sessions/{sid}/WORKING_CONTEXT.md`), not the project root.

### Context compaction (superseded: fold, not AI line removal)

`.agent/FULL_CONTEXT.md` is RENDERED from `.agent/snapshot.md` plus the write-once events in `.agent/events/`; it is never edited in place and needs no AI pruning. When `.agent/events/` has accumulated a lot of old entries, run `.claude/hooks/agent-log.sh fold`: it moves events older than 30 days into the snapshot (`--before YYYY-MM-DD` to choose the cutoff), no content is lost, and `FULL_CONTEXT.md` renders the same apart from one `registers-fold-cutoff` comment line; it refuses while events are uncovered, so review the registers and run `compact-readiness.sh --mark` first. Re-hydration reads a bounded slice of it (`/rehydrate`), so the size of the rendered file is not a problem in itself. The old procedure (send the file to a backend, delete the lines it names, append a compaction note) is retired for exactly that reason; `/prune-context` is kept only for old projects that still hand-append to `FULL_CONTEXT.md`.

## Codex delegation protocols

### Research memo

**Task:** produce a research memo with citations and implementable recommendations.

**Command:** use `codex exec` via Bash with a research prompt. Write output to `megavibe-deliverables/YYYY-MM-DD-topic.md` when the user asked for the memo and the project has that folder (and log it in STATUS.md's `Asked for` table), else to `.agent/RESEARCH/YYYY-MM-DD_topic.md` as a working note.

**Output format** (markdown):
- Findings
- Tradeoffs
- Recommendation
- Implementation checklist
- Sources (URLs, with citations for nontrivial claims)

Codex uses cached web search by default. Add `--search` for live results when freshness matters.

If Codex is unavailable, fall back to Gemini (`gemini-review.sh`) → Claude subagent — but only on a machine WITHOUT Codex: where Codex is installed and merely failed that day, Gemini's general path refuses (exit 4), so go straight to the subagent. Research is the one job where Gemini stays ahead of the subagent: neither can search the live web, and Gemini brings the larger window. Neither replaces Codex's `--search`, so say in the memo that the sources are recalled rather than fetched.

## Claude subagent protocols

The `summarizer` subagent (`.claude/agents/summarizer.md`, model: sonnet) runs when allocated by the rule above or reached through the failure fallbacks from `reviewers.sh digest-chain`. It runs on the same Claude subscription — no API key needed, always available.

**When to use:** When allocated or when Codex is unavailable or has failed. Its output is the best of the three on a context digest, but it draws on the same subscription quota the session itself is spending. Never for a review: `summarizer` is not `reviewer`, and non-negotiable 4 wants a fresh adversarial context, not a summary.

**Limitations:**
- 200K token context window (vs Gemini's ~1M) — may not fit very large FULL_CONTEXT.md files
- No web search capability (unlike Codex)
- Shares the parent session's rate limits — measured 125K tokens and 87 s on a 196 KB input, so a rehydrate here is not free even though no money changes hands

**How to invoke:** Use the Agent tool:
```
Agent(prompt="Read .agent/FULL_CONTEXT.md and produce a WORKING_CONTEXT summary (max 400 lines)...",
      subagent_type="general-purpose")
```
Or reference the custom agent if deployed: `.claude/agents/summarizer.md`
